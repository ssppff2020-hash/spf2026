## 1. 第一版抽取器与它立刻暴露的问题

写给 AI 的指令很直白：

> 「写一个脚本：输入一个装着 .html 的目录，输出纯文本镜像 + 一份 manifest（文件、字符数、词数、状态）。跳过 script/style/nav/footer/header/form/iframe。把 h1-h6 变成 Markdown 的 # 标题。编码要能自动处理。」

**坑 1：第一版直接崩。**

我（AI）在 `html_to_text()` 里写了个不存在的 `feed_and_get()`：

```
AttributeError: 'TextExtractor' object has no attribute 'feed_and_get'
```

`HTMLParser` 的用法是 `p.feed(html)` 然后 `p.text()`，没有 `feed_and_get`。**这类错误是我"凭记忆写 API"的典型症状**。修法很简单，但值得记一笔：我随后把该函数的写法改成先用 `read_bytes()` 拿到字节，再按候选编码逐个 `decode`，而不是先 `read_text` 再补救。

**坑 2：乱码（mojibake）。**

第一版对 `utf-8` 解码失败的页面直接回退到 `latin-1`。结果 Chroma 那篇里：

```
原文：  It's typically assumed that ...
抽出：  It��s typically assumed that ...
```

**根因**：那个文件其实是 UTF-8，只有个别字节坏了；整体按 latin-1 解，就把所有多字节字符全解错了。

修法 —— `decode_html()`，按优先级尝试 `<meta charset>` 声明 → `utf-8` → `cp1252` → `latin-1`，**并且不再"第一个能解就用"**，而是选出**替换字符 U+FFFD 最少**的那个：

```python
def decode_html(raw):
    head = raw[:4096].decode("ascii", errors="ignore").lower()
    meta = re.search(r'charset=["\']?([\w-]+)', head)
    cands = ([meta.group(1)] if meta else []) + ["utf-8", "cp1252", "latin-1"]
    best, best_bad = None, None
    for enc in dict.fromkeys(cands):
        try: text = raw.decode(enc)
        except (UnicodeDecodeError, LookupError): continue
        bad = text.count("�")
        if bad == 0: return text                 # 干净，直接用
        if best_bad is None or bad < best_bad:   # 都不干净就挑最不脏的
            best, best_bad = text, bad
    return best or raw.decode("utf-8", errors="replace")
```

修完后 `grep -c $'�'` 从 3 个文件命中降到 **0**。

> **教训 4**：**编码问题不要靠"能不能解出来"判断，要靠"解出来脏不脏"判断。** `latin-1` 永远不会抛异常（它对任意字节都合法），所以它是最危险的兜底 —— 它会让错误**静默通过**。

## 2. 结构性 bug：标题层级全丢了

抽完第一版，我随手看了一眼输出，发现**所有小标题都没了 `#`**：

```
Claude Code is an AI-powered coding assistant ...
Get started
Choose your environment to get started.
```

而我的代码里明明写了 h1-h6 → `#`。**读代码找到根因**：

```python
if tag in BLOCK_TAGS:              # ← h1..h6 也在 BLOCK_TAGS 里
    self.parts.append("\n")
elif re.fullmatch(r"h[1-6]", tag): # ← 永远轮不到这里执行
    self.heading = int(tag[1])
```

`BLOCK_TAGS` 里包含了 `h1..h6`，所以第一个分支永远先命中，标题分支成了死代码。

修法是**调整判断顺序**：先判标题，再判块级标签。

> **教训 5**：**分支顺序本身就是逻辑。** 这个 bug 不会报错、不会崩，只会让输出"少点东西"——
> 这类静默降级比崩溃危险得多。发现它靠的不是测试，是**人眼扫一眼输出**。

## 3. 站点外壳：一个"修过头"的教训

抽取器能跳过 `<nav>` / `<header>` / `<footer>`，但很多站的导航是**普通 `<div>`**，跳不掉。于是加了 `content_root()`：如果页面有 `<main>` 或 `<article>`，就**只抽容器里的内容**。

第一版写成"找到第一个够大的 `<main>`/`<article>` 就用"。结果：

| 文件 | 修改前 | 修改后 | 问题 |
|---|---|---|---|
| `prompt-engineering-guide` | 3402 字符 | **418 字符** | 抓到了侧边栏卡片，正文丢了 |

**这就是典型的"修过头"** —— 为了去导航，把正文也去掉了。

改成两条保险：

```python
def content_root(html):
    cands = []
    for tag in ("main", "article"):
        cands += [m.group(0) for m in re.finditer(rf"(?is)<{tag}[\s>].*?</{tag}>", html)]
    cands = [c for c in cands if len(c) > 1500]     # 太小 → 是侧栏卡片，不是正文
    return max(cands, key=len) if cands else html   # 多个候选取最长的
```

加上"容器文本至少占全文 60% 才采信，否则退回全文"：

```python
if len(narrowed) >= 1500 and len(narrowed) >= 0.6 * len(full):
    return narrowed
return full
```

修完后 `prompt-engineering-guide` 稳定在 549 字符。

**接下来是个反直觉的发现**：我把该页原始 HTML 的所有文本抽出来数了一遍 —— **3110 字符**。也就是说，这个页面 85% 的"文字"就是左侧那份罗列全部技巧名的导航菜单，正文确实只有 549 字符。**收窄是对的，不是 bug。**

> **教训 6**：**"输出变短了"要先问"短掉的是不是本来就该短"，再决定改不改。**
> 我差点为了一个不存在的 bug 去回滚一个正确的改动。

## 6. 【补记】最隐蔽的一个坑：PDF 抽取器静默损坏正文

这一条是在**翻译完成、跑质检时**才发现的，但根因在抽取阶段，所以记在这里。

### 6.1 是怎么发现的

跑完 `05_qa.py` 后，`week04` 那篇 Anthropic 官方文档的篇幅明显偏低。打开原文核对时看到这样一行：

```
Claudee Code for dattaa infraassttrruucctuturere
```

**每个字母都重复了一遍。** 再往上翻，整篇都是这样：

```
HHooww AAnntthhrrooppicic tteeaammss uussee CCllaauuddee CCooddee
```

### 6.2 为什么它能"隐身"到这一步

这是本次**最危险**的一类错误，因为它同时满足三个"不会被发现"的条件：

| 条件 | 说明 |
|---|---|
| 不报错 | `pdftotext` 正常退出，退出码 0，页数正确 |
| 输出"看起来像文本" | 依然是英文单词的形状，不是乱码方块 |
| 人眼容易滑过去 | 扫一眼只看到"哦是一篇英文文档" |

**如果我没有做"篇幅下限"检查（`中文字符 ≥ 原文词数 × 0.75`），这篇会以"翻译完成了"的状态交付出去**——
而它的原文其实是坏的。

### 6.3 量化它，然后换引擎

先量了一下损坏程度：

```python
# 判定"重复词"：奇数位字符 == 偶数位字符，如 HHooww → "Hw" + "Hw"
def doubled_rate(text):
    words = re.findall(r"[A-Za-z]{4,}", text)
    n = sum(1 for w in words
            if w[0::2].lower() == w[1::2].lower() and len(set(w[1::2])) > 1)
    return n / len(words)
```

**结果（真实数据）：**

| PDF | 页数 | poppler(`pdftotext`) | pymupdf | 判定 |
|---|---|---|---|---|
| `ai-assisted-code-review-assessment` | 9 | 0.0% / 53.2K 字符 | 0.0% / 53.1K | 两者皆可 |
| `how-anthropic-uses-claude-code` | 23 | **25.5% 损坏** / 56.2K | **0.0%** / **74.9K** | **poppler 坏了** |
| `how-openai-uses-codex` | 13 | 0.0% / 12.8K | 0.0% / 12.8K | 两者皆可 |

**注意第 2 行**：poppler 不只是把字符重复了，它输出的**总字符数还少了 33%**（56K vs 75K）——
说明它在重复一部分内容的同时，**丢了另一部分内容**。坏得比看上去更彻底。

### 6.4 修法与它变成的资产

没有为这一个文件打补丁，而是把它变成流水线的**一步**——新增 `02b_extract_pdf.py`：

> **设计**：对每个 PDF，**同时用两个引擎抽**，各自算"重复率"；
> 优先选**通过检查（< 10%）且最长**的那个；都不过关就选**最不脏**的那个。每个文件打印一行判定结果。

实际跑出来（真实输出）：

```
ok   ai-assisted-code-review-assessment   picked=poppler   53,502c  (poppler:0.0%/53,502c  pymupdf:0.0%/53,124c)
ok   how-anthropic-uses-claude-code       picked=pymupdf   74,857c  (poppler:25.5%/56,612c  pymupdf:0.0%/74,857c)
ok   how-openai-uses-codex                picked=poppler   13,085c  (poppler:0.0%/13,085c  pymupdf:0.0%/12,800c)
```

**注意它自动做了正确的选择**：三份 PDF 里，两份选 poppler（字数略多），一份选 pymupdf。
**不同引擎在不同文件上各有胜负**——这正是"双引擎 + 打分"比"固定用某一个"更好的原因。

### 6.5 连锁动作

换源后，这篇的原文从 56K 变成 75K，**内容多了 33%**，旧译文相当于基于残缺原文。
所以：**重新派单，整篇重译**，并在提示词里明确写"输出文件已存在旧译稿，请整篇覆盖"。

**这三条链式反应（发现 → 双引擎重抽 → 重译）如果少任何一环，交付出去的都是一份"看起来没问题"的错件。**

> **教训 7（最重要的一条）**：**"没报错"不等于"抽对了"。**
> 抽取类工作必须有一个**能自动说不**的指标——这次是"重复率"和"篇幅下限"。
> 两个指标都是**可计算的**，也正因为可计算，才可能在不看全文的情况下发现问题。
