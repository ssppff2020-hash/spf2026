# AI 协作日志 · 2026-10-05（三）术语表与翻译流水线

- **阶段目标**：让 33 篇译文（60 万字符）**译名统一、格式统一、不漏译**，而且换一门课还能再来一遍。
- **使用工具**：Claude Code + 17 个并行子智能体（同一份术语表、同一份规范）。
- **耗时**：约 90 分钟。

---

## 1. 先解决"怎么分工"，再解决"怎么译"

60 万字符 / 8.9 万英文词，单线程译完又慢又容易前后不一致。我的方案是三件事：

1. **术语表唯一化** —— 译名只在一处定义，所有批次读同一份；
2. **规范唯一化** —— 翻译的硬约束写在 `04_translate_prompt.md` 里，而不是散落在每个 agent 的提示词里；
3. **批次并行** —— 按周分组、按体量切批（单批 ≤ 55K 字符），一个批次一个 agent。

这样即使 17 个 agent 同时干活，**它们看到的是同一份术语表和同一份规范**，一致性来自制度而不是运气。

## 2. 术语表是怎么"长"出来的

**不是**先拍脑袋列 50 个词。做法是：

1. 从 `titles + 目录 + 高频词`里先筛出**必然会碰到的核心词**（LLM / agent / context / prompt / MCP …）；
2. 按课程五个主题域分章节：模型与提示（Week 1）、智能体与工具（Week 2–4）、安全（Week 6）、代码评审（Week 7）、SRE（Week 9）；
3. 每条都写清 **译法 + 规则 + 备注**，规则分 `translate`（译）/ `keep`（保留英文）；
4. 单独开一节 **§7 明确不译的词**（产品名、协议名、文件名）。

最终的 `glossary.csv` 有 **78 条**，覆盖验收要求的"≥50 条"。

**真正体现判断力的，是三类"难词"的处理：**

| 类型 | 例子 | 决策 | 理由 |
|---|---|---|---|
| 有公认译名 | `code review` → 代码评审 | 译 | 但**不**译"代码审查/代码回顾"，社区说的和考的通常不是一个词 |
| 无公认译名 | `scaffolding`、`vibe coding` | **保留英文** | 中文社区（2026 年）尚未形成稳定说法。硬译成"脚手架""氛围编程"反而增加理解成本。规范里写明：首现写「脚手架（scaffolding）」，其后统一用英文 |
| 一词多义 | `evaluation` / `eval` | 锁定"评测" | 不译"评估"——"评估"在中文里太泛，且与 `assessment` 撞车 |

> **一个刻意的决定**：`token`、`span`、`MCP`、`API` 这类词**一律不译**。
> 理由写进了规范 §0：「有公认译名用译名，无公认译名保留英文。」中文技术圈说 token 就是 token，译成"词元/令牌"没人这么说。

**术语表还有一条修订机制**：只追加不删除，每次改都在文末 `修订记录` 登记。当前 v1.2 记录了三轮：
- v1.0 建立 42 条核心术语（翻译前冻结）
- v1.1 补安全/SRE 章节，扩到 78 条（译 Week 6、Week 9 材料时发现缺口）
- v1.2 锁定 `code review=代码评审`、`eval=评测`、`reproducible=可复跑`，新增 §7 不译清单

## 3. 翻译规范：把"不许做的事"写死

`04_translate_prompt.md` 里最关键的不是"要译得准"，而是三条**硬约束 + 一张禁用表**：

**三条硬约束：**
1. 不许缩写、不许概括、不许跳过 ——「原文有多少段、多少个小标题，译文就必须有多少」；
2. 不许编造 —— 原文没写的数字、人名、结论一律不写；原文有错就照译并加 `> 译注：……`；
3. 术语必须查 `glossary.csv`。

**"主动禁止"比"鼓励做好"有效得多。** 我在规范 §3 直接列了一张对照表，把**实际见过的高频错译**写进"✗ 常见错译"一列：

| 英文 | ✓ 本包用 | ✗ 常见错译 |
|---|---|---|
| code review | 代码评审 | 代码审查、代码回顾 |
| agent | 智能体 | 代理、代理体 |
| context rot | 上下文腐化 | 上下文腐烂、上下文衰减 |
| evaluation | 评测 | 评估、评价 |
| reproducible | 可复跑 | 可复现 |
| vibe coding | vibe coding（不译） | 氛围编程 |

**规范里还有两个小设计，事后证明很值：**

- **统一文档头**：每篇译文开头强制 6 行 block（原文标题 / 来源 / 课程周次 / 译文状态 / 术语依据 / 覆盖声明）。
  → 好处不只是好看：`05_qa.py` 就是靠解析这 6 行的「原文标题」**自动把译稿和原文配对**的。
  **格式即接口**——为了让 QA 能自动跑，我在格式上提前留了钩子。
- **NEW-TERM 回填协议**：译者遇到术语表没覆盖的词，首现写「中文（English）」，并在文件末尾留一行
  `<!-- NEW-TERM: english | 中文 -->`。→ QA 脚本会把这些收集成"待回填清单"，术语表因此能**持续生长**。

## 4. 先跑 3 篇试验，再铺开 14 批

**没有一次性启动 17 个 agent。** 先挑了 3 个体量小、类型不同的批次试跑：

| 试验批次 | 文件 | 为什么挑它 |
|---|---|---|
| week3-A | `specs-are-the-new-source-code`、`how-long-contexts-fail` | 标准博客，验证基本流程 |
| week5 | `warp-vs-claude-code`、`how-warp-uses-warp` | **含一篇 Notion 抽取的畸形文本**（有序列表编号全变成 `1.`） |
| week4 | `claude-code-best-practices` | **含站点导航残留**，专门验证译者会不会把导航也译了 |

**检查试验稿时发现的（读的是 AI 实际产出的原文）**：

✅ **做对的**：
- 文档头 6 行格式完全正确；
- 术语零失误：全文用「智能体」「代码评审」「大语言模型」「拉取请求」「模型上下文协议（MCP）」；
- 结构完整：原文的每个 `##` 小节都在；
- 代码块原样保留（`curl -fsSL https://claude.ai/install.sh | bash` 未被翻译破坏）。

✅ **超出预期的**：译者**主动**给抽取损坏处加了译注，例如：

> 原文抽取把 `https://claude.ai/install.ps1` 压成了 `https: // claude.ai / install.ps1`
> → 译文还原成正确 URL，并加了一行：`> 译注：原文的 HTML 抽取把 URL 里的空格压了出来……`

这正是规范 §0 第 2 条想要的：**发现问题要说出来，而不是静默"修好"**。

⚠️ **仍有的小瑕疵**（记录下来，未阻塞）：
- 页脚残留：「本页对你有帮助吗？」「回复由 AI 生成，可能包含错误。」被译了出来 → **这直接催生了 `05_qa.py` 的外壳残留扫描**；
- 少量标点缺失。

**成本账**：一次试验只花了 3 个 agent 的额度，却避免了一个格式错误在 17 个批次里被复制 17 遍。
**先小规模验证"格式契约"，再规模化**，这是今天省下时间最多的一条。

## 5. 铺开：33 篇 → 17 个批次

批次划分规则（写进了 `pipeline/config.yaml`）：

- **按周分组**：尽量让一个 agent 处理同一周的阅读，语境连贯；
- **单批上限 55000 字符**：超过就拆（如 Week 6 的 5 篇拆成 4 批）；
- **长短搭配**：把一篇 30K 的和两篇 5K 的放一起，避免某个 agent 空转。

最终 17 个批次覆盖全部 33 篇。每个 agent 的提示词只包含三样东西：
**它要译的文件清单与输出路径** + **"先读规范和术语表"的指令** + **该批的特殊注意事项**（比如"第 2 篇是字幕转录稿，口语化处理""参考文献保留英文不译"）。

规范本身不在提示词里重复，而是让 agent 去读同一个文件 —— **单一事实源**。

> **一个细节**：给长文批次（如 5.6 万字符的 Anthropic 官方文档）的提示词里，我额外加了一句
> 「请**分批读入**（Read 支持 offset/limit），逐批翻译后累加写入同一输出文件，**不要因为长就概括或跳译**」。
> 因为长文最常见的失败模式不是译错，而是**中间悄悄略过几段**。
