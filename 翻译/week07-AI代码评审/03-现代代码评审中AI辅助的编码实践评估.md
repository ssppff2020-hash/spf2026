## 摘要

现代代码评审是一个过程：代码作者提交的增量式代码贡献，在合并进版本控制系统之前，先由一位或多位同行评审。现代代码评审的一个重要环节，是核实代码贡献是否遵守最佳实践。其中一部分最佳实践可以自动核实，但核实其他最佳实践通常留给人工评审者。本文报告了 AutoCommenter 的开发、部署与评测，这是一个由大语言模型（Large Language Model，LLM）支撑的系统，能够自动学习并执行编码最佳实践。我们为四种编程语言（C++、Java、Python 和 Go）实现了 AutoCommenter，并在一个大型工业环境中评测了它的性能与采纳情况。我们的评测表明，一个用于学习和执行编码最佳实践的端到端系统是可行的，并且对开发者工作流有正向影响。此外，本文报告了把这样一个系统部署给数万名开发者时所遇到的挑战，以及相应的经验教训。

## 1 引言

现代代码评审 [21, 23]（相对于整体式代码评审 [8]）多年来在开源环境和工业环境中自然生长起来。一套常见的同行评审准则已经形成 [5, 20, 21]，其中就包括编码最佳实践。许多公司、项目、甚至编程语言都以「风格指南」[1–4]的形式正式定义了它们，这些指南通常涵盖以下几个方面：

- 格式：行宽限制、空白与缩进的使用、圆括号与方括号的位置，等等；
- 命名：大小写、简洁性、描述性，等等；
- 文档：文件级注释、函数级注释及其他注释的预期位置与内容；
- 语言特性：在不同（代码）语境中对特定语言特性的使用；
- 代码惯用法：使用代码惯用法来提升代码的清晰性、模块化程度和可维护性。

开发者普遍反馈对现代代码评审流程满意 [23, 28]。它的主要好处之一，是让那些不熟悉代码库、特定语言特性或常见代码惯用法的代码作者获得学习体验。在评审中，资深开发者会向代码作者讲解最佳实践，同时评审（并了解）代码贡献及其影响。

像 linter [15] 这样的静态分析工具可以自动核实代码是否遵守某些最佳实践（例如格式规则），有些工具甚至能自动修复违规。但细致的准则、或者带有例外的准则，很难被完整地自动核实（例如命名约定，以及遗留代码中有正当理由的偏离），还有一些准则根本无法用精确规则来刻画（例如代码注释的清晰性与具体程度），只能依靠人的判断和开发者的集体知识。因此，人们普遍预期由人工评审者来检查代码改动是否违反最佳实践。

代码评审流程最大的成本是所花费的时间，尤其是资深开发者投入的时间。即使已经做了大量自动化，并且尽量让流程保持轻量，一个开发者每天仍很容易在这个任务上投入好几个小时 [23]。

机器学习最近的进展，特别是大语言模型（LLM）的能力，表明 LLM 适合做代码评审自动化（例如 [11, 16, 17, 24–26]）。然而，围绕在规模化场景下部署端到端系统的软件工程挑战仍然没有被探索过。同样，这类系统在整体有效性和用户接受度上的外部评测也是缺失的。

本文研究的是：能否部分自动化代码评审流程，具体来说就是自动检测最佳实践违规，从而为代码作者提供及时的反馈，并让评审者能专注于整体功能。具体而言，本文报告了我们在 Google 的工业环境中开发、部署与评测 AutoCommenter——一个自动化的代码评审助手——的经验。它目前每天被数万名开发者使用。

总而言之，本文的贡献是：

- 一个基于 LLM 的代码评审助手系统的通用架构（第 3 节）。
- 工具校准以及向数万名开发者部署的描述（第 4 节）。
- 对系统的评测（第 5 节）。
- 经验教训的总结与讨论（第 6 节）。

## 2 背景

AutoCommenter 是在 Google 的大型工业环境中开发的。Google 的现代代码评审实践与其他工业项目和开源项目类似 [23]。

### 2.1 代码评审流程

Google 的代码评审流程已经非常成熟，它基于变更（change），并有工具辅助。Ivanković 等人 [12] 和 Petrović 等人 [18] 对这一流程给出了详细总结。对代码库的每一次变更都必须至少由另一位开发者评审。每天有数万次代码库变更走完评审流程，数万名开发者作为代码作者和评审者参与其中。

作者与评审者通过代码评审系统交换评论，评审则随着受变更影响的文件快照（snapshot）向前推进。每条评审者评论都附着在特定文件快照中特定的行与列范围上。要解决一条评论，作者通常会在本地副本中修改该文件，并导出一个新快照用于下一轮代码评审。当作者和所有评审者都满意，并且没有任何自动化分析阻塞合并时，代码就被合并进代码库。

代码评审流程中最昂贵的部分，是代码作者和评审者「全程照看」（shepherding）一次变更所花的时间（从最初写代码，到处理评审者评论并确保所有自动化分析通过，最后把变更合并进代码库）。虽然流程已经用自动化系统做了优化——在评审之前分析代码（尤其是无需人工介入的自动代码格式化）——代码评审仍然每年耗费数千开发者年。因此，哪怕只是个位数百分比的节省，也会转化为可观的业务影响。

### 2.2 最佳实践

最佳实践是指某种被认为更优的特定编程语言用法，而最佳实践文档描述它应当如何应用、能带来什么好处。最佳实践 URL 指的是某份最佳实践文档或其中的某个具体小节，「最佳实践违规」（best practice violation）指的是某一处不遵守最佳实践、但可以改到遵守的代码。如果从上下文看不会歧义，我们就用 URL 和「违规」分别指代最佳实践 URL 和最佳实践违规。

Google 的中心代码库包含多种语言的代码，其中 C++、Java、Python 和 Go 都各自超过 1 亿行 [19]。有 15 种不同语言拥有对所有开发者开放的正规风格指南。其中许多语言还有额外的语言入门读物、核心库文档，以及「每周小贴士」式的通讯。这些材料虽然不像风格指南那样被严格执行，但在代码评审中被频繁引用。有些语言的这类文档多达数百页。代码作者和评审者都被期望核实代码遵守了所有最佳实践。

十多年前引入的一项名为「可读性」（readability）的正式机制，确保最佳实践被一致地遵守。某种语言下的专职风格专家被称为「readability 导师」，他们指导缺乏经验的开发者达到该语言的熟练水平 [23]。readability 导师通常用几句话概括一条最佳实践，并在评论末尾附上一个 URL 供变更作者参考。图 1 展示了一条由 readability 导师发布的评论示例。

readability 流程也有一些缺点。对作者来说，它因为增加了额外的评审轮次而拉长了开发时间。对 readability 导师来说，这可能变成一项单调且耗时的任务。它要求掌握数百条不断演进的最佳实践，包括识别并废弃过时的规则，并在代码评审系统中把它们（连同相关链接）记录下来。此外，它还要求持续跟踪，有时要经过多轮迭代，确保所有违规都已被修正。

## 3 方法

针对第 2.1 节和第 2.2 节描述的挑战，我们开发了 AutoCommenter，一个自动检测最佳实践违规的代码分析工具。它的目标是为代码作者提供及时反馈，减少人工做最佳实践评审的需要，从而让评审者能专注于代码功能。

### 3.1 模型与任务定义

要自动化最佳实践分析，需要一个能够表示源代码、定位违规位置、并识别被违反的最佳实践的模型。我们采用基于 T5 的传统 Transformer 方法，使用 T5X [22]，指向一个文本到文本（text-to-text）的转换任务。

最佳实践分析是一个多任务大序列模型中的一项任务。除了 T5 的标准预训练任务——span 去噪（预测被遮蔽的 token）——之外，用于训练该模型的其他任务还包括代码评审评论的解决、下一次编辑预测、变量重命名和构建错误修复 [9]。训练语料包含超过 30 亿个样本，其中最佳实践分析数据集贡献约 80 万个样本。模型用这类模型惯用的标准交叉熵损失训练，并以最大化序列准确率（sequence accuracy）指标为目标做了调优，即对每个样本预测出精确的目标文本。

对于最佳实践分析，模型的输入是一个任务提示词加源代码，目标是源代码中的一个位置以及一条最佳实践违规对应的 URL。任务提示词被格式化为一段固定文本的代码注释，使用该编程语言相应的注释风格。它用自然语言描述任务，并置于源代码之前，而源代码是某一个文件的直接文本表示。如果输入超过模型的上下文窗口，就会被截断。位置是源代码中的字节偏移，URL 则指向被违反的最佳实践。目标格式由一种领域特定语言定义，其中有一个特殊情况是「空」目标，表示没有任何违规。除了目标之外，模型还会输出一个 0 到 1 之间的置信度分数。

来看下面这个 Go 语言的输入/目标示例。输入：

```
/ / [∗] Task : Check language best practices .
/ / Package a d d i t i o n p r o v i d e s Add package addition
/ / Return a sum
func Add ( value1 , v a l u e 2 i n t ) i n t {
return value1 + value2 }
```

目标：

```
INSERT 1 5 3 COMMENT h t t p s : / / go . d e v / d o c / comment # f u n c
```

输入的第一行是固定文本的任务提示词；其余部分是源代码。目标给出了位置（字节偏移 153 对应 `Add` 函数的开头）以及一个 go.dev 的 URL，指向 Go 语言风格指南中恰好被该函数注释违反的部分（在此例中是「注释应以函数名开头」这一惯常做法）。注意，目标可能包含零个、一个或多个（拼接起来的）位置-URL 对，取决于源代码中有多少处违规。

### 3.2 模型训练

图 2 展示了模型训练流水线的架构，它由三部分组成。我们把数据集创建拆成两步（预处理和筛选），因为第一步要在远远更大的数据量上运行，成本明显更高。预处理步骤的输出与模型的输入/目标表示无关。这种分离提升了功能迭代速度，因为可以在样本表示和其他样本级调整上快速迭代。预处理步骤使用容错调度系统，周期性地抽取相关的代码评论，以确保新数据随时可用。

#### 3.2.1 大规模预处理

训练样本来自真实的代码评审数据，但并非所有代码评论都适合用于模型训练。因此，预处理步骤会识别出「相关代码评论」——即包含指向最佳实践文档的 URL 的人工撰写评论。对每条评论，预处理步骤随后收集对应的源代码和相关元数据，包括评论在源代码中的位置及其创建时间。这一步的输出是一组相关代码评论，每条都带有为模型训练筛选样本所需的全部数据。

#### 3.2.2 数据集筛选

数据集筛选是一个单一的、按需触发的处理步骤，用 Beam1 流水线实现。它依据第 3.1 节描述的输入/目标格式，把每一条相关代码评论转换成标准的 TensorFlow Example 数据结构。

#### 3.2.3 训练与微调

筛选好的样本直接用于模型训练和评测。我们在一个 TPU 集群上使用 T5X 框架 [22]，每 1000 步保存一次模型检查点，并用 Tensorboard 监控训练。

### 3.3 模型选择

在历史数据上做的两次内在评测（intrinsic evaluation），决定我们对模型检查点、置信度阈值和解码策略的选择。第一次评测在验证集和测试集上进行，给出按文件粒度的精确率（precision）和召回率（recall）估计。第二次评测在完整的历史代码评审上进行，给出每次代码评审的评论总数估计，从而说明开发者与 AutoCommenter 交互的频繁程度。

#### 3.3.1 在验证集与测试集上的评测

我们按时间切分数据集，以确保模型没有在验证集和测试集中那些代码评论的未来代码评审快照上训练过。在我们的数据集中，85% 的文件恰好有一条相关代码评论，11% 有两条，4% 有三条或更多。我们把一次预测定义为正确，当且仅当预测的代码位置和 URL 与期望值匹配（不考虑顺序）。

- 缺少引用：评审者可能评论了某个问题，但没有附上 URL 作为引用。
- 选择性评论：评审者可能只评论一次某个问题，期望作者在整份代码里都应用修复。
- 专业程度或关注点不同：评审者可能并不熟悉所有最佳实践，或者只是在某次代码评审的上下文中选择不评论某个问题（例如只关注被改动的代码）。

#### 3.3.2 在完整历史代码评审上的评测

为了准确衡量真实环境中可能的评论量，我们在一个历史代码评审集合上评测 AutoCommenter，使用特定的模型检查点和阈值。预测出的评论不会被追溯性地发布到代码评审系统中，而是记录在数据库里以供分析。这让我们能够估计预期的发布频率——既按文件粒度，也按代码评审粒度。由于开发者面对的是一整组进入代码评审的代码变更，与 AutoCommenter 交互，所以这一步评测是投产部署前的重要环节。作为额外收益，这一步还允许做进一步的优化，并评测不同用户群、不同编程语言等条件下的发布频率。

### 3.4 推理基础设施

AutoCommenter 的核心是一个中心化的最佳实践分析服务。该服务以一个或多个源文件作为输入进行分析。对每个文件，它构造模型输入（第 3.1 节），编码成标准的 TensorFlow Example 数据结构，然后查询模型。模型本身由一个模型服务提供，该服务用 TensorFlow 的 Example 数据结构作为与领域无关的输入输出格式。最后，最佳实践分析服务执行一系列过滤步骤（第 4 节），抑制低质量的预测，并返回剩余的预测结果。

### 3.5 IDE 与代码评审系统集成

开发者通过两种方式与 AutoCommenter 的分析服务交互——直接通过 IDE 插件，或者间接通过代码评审系统。代码评审系统被 Google 的所有开发者使用，IDE 则被几乎所有人使用。

AutoCommenter 的评论在 IDE 中以诊断信息的形式出现，带有蓝色波浪下划线，覆盖相关的代码片段。把鼠标悬停在被划线的代码上，会显示完整评论，其中包含该最佳实践的简洁摘要，以及指向相关最佳实践文档的可点击链接。这些嵌入式信息省去了开发者为了解不熟悉的最佳实践而在 IDE 和网页浏览器之间来回切换的需要，从而简化了工作流。由于 IDE 中的评论需要实时生成，我们力求把生成评论的延迟控制在亚秒级。

在代码评审系统中，AutoCommenter 在每次更新后（即每个新的代码评审快照上）运行，如果检测到违规就自动发布评论。自动化工具产生的评论在视觉上与人工产生的评论相似，但背景颜色不同。

图 3 展示了 AutoCommenter 在代码评审系统中生成并发布的一条评论示例。注意（右侧的）点赞和点踩按钮，作者和评审者如果觉得某条评论特别有用或没用，可以点击它们。还要注意（左侧的）「Please fix」按钮，它对评审者可见。如果点击它，就会生成一条新评论，表明该评审者认为这条评论很重要，必须在代码合并进代码库之前解决。这些反馈按钮是代码评审系统中的标准功能，出现在自动化工具生成的所有评论上（例如 [7, 13]），为一个工具的用户接受度提供了信号。IDE 也提供了类似的反馈机制。

### 4.1 选择阈值与解码策略

#### 4.1.1 阈值

在初始部署期间，我们希望谨慎地维护开发者对 AutoCommenter 的信任，于是从一个较高的置信度阈值 ������ = 0.98 开始。我们人工抽样了几百条结果，观察到阈值以下的预测中约有 80% 仍然是正确的——也就是说，在 ������ = 0.98 时假阴性率非常高。此外，我们观察到 Python 中的预测显示出明显不同的置信度分数分布，受到阈值化不成比例的影响。我们猜测原因是训练数据集的构成（不同 URL 的数量与 URL 频率）以及最佳实践文档的具体程度，但把更深入的调查留给了未来工作。我们尝试过按语言设置阈值，但没有效果，因为每种语言用单一阈值仍然无法充分反映模型正确预测数百条多样化最佳实践的能力。这导致预测出的 URL 缺乏多样性，因为模型倾向于给某些 URL 打出比另一些更高的分数，与正确与否无关。这些观察引出了对 AutoCommenter 的第一次重大改动：基于验证集上的内在评测，按 URL 计算阈值。

#### 4.1.2 解码

在完整历史代码评审上使用按 URL 的阈值加贪心解码做评测，结果显示 AutoCommenter 在 6% 的被改动文件中检测到了违规。然而，其中 80% 的评论会被发布在作者并未修改的代码行上。开发者通常不会对未改动的代码采取行动。因此，AutoCommenter 会过滤掉对未改动代码行生成的评论，把被改动文件中的评论比例降到 1.3%。为了提高这个比例，我们试验了不同的解码策略：贪心（默认）、束搜索（beam search）、top-k 和 top-p 采样。我们最终选定了束搜索（生成 ������ = 4 个候选回复），它把发布频率提高到原来的三倍，达到 3.9%。它还带来了显著更高的 URL 多样性：发布最频繁的前 10 个 URL 占全部评论的 41%，而贪心搜索是 80%。

在选择用于部署的解码策略时，延迟是另一个重要方面。虽然束搜索提高了发布频率和多样性，但推理明显变慢了（延迟中位数为 2 秒）。考虑到这种延迟对 IDE 中的交互式使用来说是不可接受的，我们最终决定：代码评审系统使用束搜索，IDE 使用贪心搜索。

### 4.2 抑制过时的最佳实践

在把 AutoCommenter 发布给约 3000 名自愿的第一批采用者之后，我们注意到用户在几天内提交了大量问题报告。其中许多对应同一个 URL2，该文档描述的是与 Python import 相关的最佳实践。然而，某些类型名的规范来源在 Python 3.9 中变了，这条最佳实践也在 2022 年初发生了变化。由于我们的训练数据延伸到 2022 年之前，其中包含了若干已不再适用的最佳实践评论。我们意识到这是一个反复出现的模式：随着语言演进，或者新库被引入，最佳实践也会演进。缓解这个问题的一种办法是过滤掉这类数据（每当规则变化时），然后重新训练模型。但这既耗时又耗资源：它需要完整地重新生成数据、训练模型、评测并铺开上线。在过渡期间，「过时的」模型要么必须被关掉，造成系统停机，要么必须抑制受影响的预测。否则，系统可能很快失去开发者的信任。我们选择抑制特定的最佳实践预测，用条件过滤（在源代码上做正则表达式匹配）来实现，原因有两个。第一，它可以动态部署并立即生效。第二，它允许对预测做细粒度的过滤。

### 4.3 对选定评论做独立评分

在早期使用几个月后，我们观察到有用率在约 54% 处趋于平稳。为了理解原因、找出改进空间，并为更大范围的部署做准备，我们在 2023 年 4 月开展了一项独立的人工评分研究，分析了在第一批采用者部署期间收到开发者反馈的约 370 条已发布评论的样本。

为了收集对评论有用性的多元视角，我们招募了 15 名评分者——来自合作团队的开发者。我们请他们对 AutoCommenter 那些收到明确用户反馈的评论打分。我们没有向评分者展示原始的用户反馈，以免影响他们的评价。评分者根据所链接的最佳实践和周边代码，评测每条评论的有用性。我们指示他们重点关注评论的正确性，但同时也要考虑这条评论对他们作为作者而言是否可执行（例如，一条技术正确、但在具体场景下看起来不值得解决的评论，他们会不会去解决）。我们还鼓励他们对每条评论给出自由形式的反馈。

评分者评测得出的有用率是 60%，比同一批评论上开发者反馈得到的 54% 略高，但远低于我们为更大范围部署设定的 80% 目标。

这项研究最有趣的发现是：「无用」评论存在清晰的模式。以下是一些例子：

多个话题或复杂话题：例如，有一个 URL 指向一个小节，其中描述了多条与 Python linter 交互的准则，包括它经常触发的情况以及抑制它的方法。作者可能很难理解某条已发布的评论到底指的是哪条具体准则、又该如何解决。类似地，关于如何在 C++ 中写好函数文档的指引是整整一页密集的文字。评分者经常指出，最佳实践（以及 AutoCommenter 的简洁摘要）与实际代码之间存在脱节，即使代码中确实含有相关违规。

高质量摘要的重要性：评分者经常发现，AutoCommenter 的摘要——通过抓取文档源码生成，有时还会缺失——未能充分说明所引用准则与评论/代码之间的相关性。

主观且可能引起争议的话题：一个例子是避免在库代码中使用标志位（flag）。标志位用在库里会引发问题，但有些库本身就被设计成通过标志位来配置许多特性。此外，遗留代码可能并不遵守这条准则，评审者也不会强制执行它。模型没有学到这些细微差别，有时会在作者给已有库新增一个标志位时预测出一条违规。

某些准则上的系统性模型错误：一个有趣的例子是一条准则，它提倡在 C++ vector 上优先使用成员函数 `push_back` 而不是 `emplace_back`——当两个函数可以用相同参数达到相同效果时。模型学会了预测这条，但它也会在 `emplace_back` 确实更合适的情况下预测它，还会在某个无关类型有一个叫 `push_back` 的成员函数时预测它。

正确但价值低的评论：代码注释中句子末尾缺少句号，往往被人工作为评审者所容忍。虽然技术上正确，但要求作者回到 IDE 去修这个问题，净价值可能是负的。

评分研究的洞见给 AutoCommenter 带来了两处改动。第一，评分研究识别出 17 个不可执行的 URL，抑制它们后，在开发者反馈上的历史有用率从 54% 提高到 66%，在评分者反馈上从 60% 提高到 74%。我们进一步分析了与这些相似但未被评分的 URL 相关联的评论，又抑制了 5 个。第二，我们审查并人工更新了所有高频发布的 URL 的摘要。这些改动合在一起，足以达到部署下一阶段所需的 80% 有用率目标。

### 4.4 A/B 实验

2023 年 7 月，我们在一次 A/B 实验中把 AutoCommenter 部署给约一半的开发者。我们把开发者随机分配到实验组（启用 AutoCommenter）和对照组（禁用 AutoCommenter）。我们基于开发者邮箱地址 SHA256 哈希的最后几位做随机化，并核实两组在规模和构成上没有差异，包括任职年限、资历、编程语言和业务部门的分布。我们还确认，实验开始前，实验中测量的所有变量在对照组和实验组之间都没有差异。实验期间的评论发布频率符合预期（第 4.1 节）。

我们没有检测到以下任何一项有统计上显著的变化：代码评审的总时长、开发者主动花在代码评审上的时间、作者与评审者之间评论-回复的迭代次数。不过，我们确实检测到编码速度有轻微提升。我们猜测，这种正向效应来自为查阅文档而切换上下文的次数减少。更深入的调查留待未来工作。基于这些结果，我们得出结论：没有不良影响，并于 2023 年 10 月把 AutoCommenter 部署给了所有开发者。

## 5 评测

基于有用率和自 2023 年 3 月以来收集到的用户反馈，我们得出结论：开发者总体上对 AutoCommenter 产生的评论是满意的。我们通过分析用户反馈，持续改进数据集准备、阈值、URL 抑制和摘要，以确保 AutoCommenter 对开发者工作流产生高度的正向影响。

除了开发者满意度之外，在面向全体 Google 开发者广泛发布几个月后，我们还评测了 AutoCommenter 性能的另外三个方面：

(1) 评论解决率：开发者多久会修改代码来解决 AutoCommenter 发布的评论？
(2) AutoCommenter 与人工评论的对比：AutoCommenter 的评论在多大程度上覆盖了人工评审者在评论中引用的最佳实践文档？
(3) AutoCommenter 与 linter 的对比：AutoCommenter 的产出在多大程度上超越了传统静态分析工具的能力？

### 5.1 评论解决率

开发者很少通过点击代码评审系统和 IDE 中的点赞/点踩按钮、以及代码评审系统中的「Please fix」按钮（图 3）来对 AutoCommenter 的评论给出明确反馈：代码评审系统中约 10% 的自动评论、IDE 中 2% 的诊断收到了明确反馈，这与 Google 其他自动化分析的反馈率相当。与此同时，开发者会悬停查看 AutoCommenter 约 50% 的 IDE 诊断，而先前的工作表明，开发者经常在不给出明确反馈的情况下就解决自动化评论 [18]。为了评测开发者多久会解决 AutoCommenter 的评论，我们做了一次离线分析，估计由后续代码改动所解决的评论占比。

为分析评论解决情况，我们抽取了 AutoCommenter 有过自动评论的文件所涉及的历史变更。对每一次变更，我们抽取评论最初发布时的快照，以及开发者最终合并进代码库的快照。每条评论覆盖一个特定的行范围。我们在这两个快照之间使用一种基于 AST 的自动行映射方法 [18]，来识别那些模型最初在第一个快照上预测到了、但在合并快照上没有预测到的评论。这样的快照对表明评论可能已被解决，但也不排除是无关的代码改动导致某条评论不再被预测出来。

对 6000 对快照的自动分析显示，在 50% 的情况下，评论在其最初发布的那些行上已经从提交的快照中消失了。我们人工抽检了 40 对这样的快照。我们发现，在 80% 的情况下，作者所做的一处改动直接解决了该已发布评论所描述的问题。因此，我们估计评论解决率约为 40%，这明显高于获得明确正向反馈的评论占全部评论的比例。

### 5.2 AutoCommenter 与人工评论的对比

图 5 比较了生产环境中 AutoCommenter 生成的自动评论与训练数据中的人工评论，按（指向最佳实践文档的）唯一 URL 统计的评论累积分布。横轴是 URL 的排名，做法是把自动评论中用过的所有 URL 按频率排序。例如，使用最频繁的 URL 排名第 1，占全部自动评论的 9.9%。同一个 URL 出现在训练数据中 4.3% 的人工撰写评论里。总体而言，AutoCommenter 为 330 个不同的 URL 生成过评论。AutoCommenter 使用到的 URL 集合覆盖了带最佳实践 URL 的历史人工评论的 68%。这是个好结果：它表明 AutoCommenter 并没有把注意力放在评审者很少引用的冷门最佳实践上。

另一方面，尽管使用了束搜索，URL 多样性仍然相对较低。前 85 个 URL 占了 AutoCommenter 生成评论的 90%。同一组 URL 覆盖了带最佳实践 URL 的人工评论的 35%。在保持准确率和低延迟的前提下，提高自动评论的 URL 多样性和最佳实践覆盖度，是我们的首要任务之一。

### 5.3 AutoCommenter 与 linter 的对比

为了理解 AutoCommenter 在多大程度上提供了 linter 之外的价值——linter 能高效且精确地检查某些最佳实践——我们抽样了预测最频繁的前 50 条违规，也就是图 5 中的前 50 个 URL。对抽到的每个 URL，我们查看它的最佳实践文档，并确定 (1) 最佳实践类型（第 1 节），以及 (2) 是否存在（或能否容易地构建出）检测对应违规的 linter。具体来说，三位作者（每人在构建静态分析工具上都有超过 10 年的经验）阅读了文档，并独立地对这些 URL 做了分类。在最佳实践类型上没有分歧，但就约 15% 的 URL 而言，在「能否容易地为它构建 linter」这一点上存在分歧。三位作者通过多数表决和讨论解决了这些分歧。分歧源于最佳实践本身有歧义，或者包含多条准则。例如，检查是否存在代码文档相对直接，但判断有正当理由的例外以及内容是否清晰就没那么简单了。

图 6 展示了抽样的 50 个 URL 的分布，按类型以及违规是否可被 linter 检测来拆分。这些最佳实践中有 33/50（66%）的违规检测超出了传统静态分析的范围。

## 6 经验教训

基于我们开发和部署 AutoCommenter 的经验，我们总结出几条关键的经验教训：

- 补充传统分析：AutoCommenter 由 LLM 支撑的方法，为人工评审者频繁引用的最佳实践中的 68% 生成了评论。其中许多超出了传统静态分析的范围。
- 内在评测与真实世界表现的对比：内在评测与真实世界表现可能差异很大：我们的内在评测使用真实世界人工评论构成的数据集，配合当时最先进的模型架构和训练流程，指出了一个有前景的模型，但我们的外部评测和系统改进对于成功部署来说被证明是不可或缺的。
- 监控用户接受度至关重要：哪怕只有少数几次负面的用户体验，也可能侵蚀对自动化系统的信任。持续监控并分析真实世界的反馈，对于发现这类情况并找出补救办法至关重要。就 AutoCommenter 而言，一个简单的抑制机制就足以把用户接受度大幅提升到 80% 以上，而且没有在有效性上做出重大牺牲。

## 7 相关工作

Johnson [15] 在大约 50 年前的 1977 年引入了 C linter。在那 50 年里，关于自动化静态分析产生了相当多的研究成果：Heckman 和 Williams [10] 最近的一篇文献综述识别出 17,571 篇论文。许多研究探讨开发者如何与静态分析交互。Johnson 等人 [14] 探讨了开发者在使用静态分析时面临的挑战。他们研究的结果凸显了与既有开发者工作流良好集成的重要性，以及建立并维护对工具信任的重要性。Vassallo 等人 [27] 探讨了开发者在不同场景（包括编码和代码评审）中如何与静态分析交互。他们也发现，集成进既有工作流对开发者是否愿意使用这些工具起着主要作用，并且高质量的结果极其重要。Beller 等人 [6] 研究了大量开源项目中静态代码分析的使用情况。在诸多发现中，他们强调了自动化分析的使用方式与应当的使用方式因编程语言而异。

相比之下，用机器学习做代码分析是一个相对较新、理解也较少的领域。近期有不少论文（例如 Hong 等人 [11]、Li 等人 [16]、Li 等人 [17]、Thongtanunam 等人 [24]、Tufano 等人 [25] 和 Tufano 等人 [26]）报告了模型评测，并提出了用于自动化代码评审的工具。虽然这些模型和评审评论生成任务与本文提出的模型非常相似，但它们的评测大多集中在历史数据集上。正如第 3.3.1 节所讨论的，只基于历史评论的内在评测有一定局限，有时无法预测真实世界的表现。Frömmgen 等人 [9] 最近的另一篇论文展示了对一个在线系统的评测，但任务是相反的：从评论生成代码，而不是从代码生成评论。

## 8 结论

核实代码是否遵守最佳实践，是现代代码评审流程中的一项常见任务。有些最佳实践可以用 linter 之类的传统工具自动核实，但许多仍需要资深开发者的知识和判断，这需要时间和精力。

本文报告了我们开发、部署与评测 AutoCommenter 的经验，这是一个由 LLM 支撑的代码评审助手系统。具体来说，它呈现了从任务与模型设计，到内在评测与系统校准，再到分阶段铺开与终端用户评测的完整过程。

评测结果表明，开发一个能力远超传统工具的端到端系统是可行的，同时还能达到很高的终端用户接受度。这些结果是朝部署复杂的代码评审助手和自动化代码评审迈出的有前景的第一步。

我们的首要任务是通过把 AutoCommenter 设计成具有非常高的精确率，来确保良好的开发者体验。虽然召回率不是主要关注点，但我们认识到它的重要性，并计划探索模型和系统架构上可以怎样改动来提升召回率。例如，我们 2022 年使用的模型在当时是最先进的。然而它的上下文窗口只有 2048 个 token，只够容纳约 200 行代码。当前最先进的模型在训练时上下文窗口有数万个 token，推理时超过一百万个 token。这一跃升为新的功能、以及现有功能的显著改进打开了机会。
