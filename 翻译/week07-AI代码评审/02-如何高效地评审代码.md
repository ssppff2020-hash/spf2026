作为 GitHub 的一名资深工程师（staff engineer），代码评审是我日常工作中最主要的方向之一。过去八年里，我评审了 7000 多个拉取请求（PR）。为什么这么多？因为代码评审对做出好软件至关重要，多一双眼睛往往能发现你自己漏掉的问题。

我把代码评审看作我工作中最重要的部分之一。实际上，只要看到同事有拉取请求可以评审了，我宁愿放下自己手头的分支，先去评审他们提出的改动。毕竟，他们的拉取请求已经闯过了持续集成（CI）的重重关卡，也达到了他们自己认定的「完成」标准，所以它大概率比我手上还没做完的工作更接近可交付状态。与其在自己的代码上再耗上不确定的一段时间，我更愿意先把他们的代码推过终点线。

我给出反馈越早——「这里可能为 nil，会报错」「这看起来是个 n+1 查询」「这里最好加个方法签名」——这些反馈就能越快被处理，bug 越快被干掉，功能越快上线。

我想分享一下我做代码评审的方式，希望我们都能交付更好的代码。

## 什么是代码评审？

严格来说，代码评审——在 GitHub 上就是拉取请求评审——让协作者可以评论拉取请求里提出的改动、表明自己对改动的赞成，或者在拉取请求合并之前要求继续修改。

我把拉取请求看作一次对话的开始。我把它读作作者在说：「我认为这个改动比我们现在的做法更好。」代码评审是塑造产品实现方式的好机会。作为评审者，我的工作就是和作者来回讨论，通过提问、质疑假设，总体上充当第二双眼睛，帮他们把代码改得更好。

## 打磨你的代码评审流程

### 如何找到待评审的拉取请求

我几乎住在 GitHub 通知收件箱里。它是我在浏览器里固定的少数几个标签页之一，所以随时都能打开。无论是在等 CI、手头任务之间的空档、一天刚开始，还是随便有点空闲，我都喜欢去看一眼收件箱。我评审的拉取请求大多是在那里找到的。GitHub 的各团队往往会有一个固定的 Slack 频道作为大本营，那里是分享「可评审」拉取请求的好地方——这也是我发现拉取请求的另一条主要途径。

我在用 GitHub 的 Slack 集成时效果也不错：可以把一个 Slack 频道订阅到与我团队相关的新拉取请求上。为了筛选哪些拉取请求会出现在 Slack 里，我会用一个团队专属的标签，然后在 Slack 里执行订阅命令，比如 `/github subscribe your/repo pulls +label:"your-team-label"`。

我喜欢用这样的查询来搜索可能需要评审的未处理拉取请求：`is:open archived:false is:pr org:github -is:draft team-review-requested:github/relevant-codeowner-team`。用这个查询，我能找到 GitHub 组织里处于打开状态、未归档、不是草稿、并且把相关代码负责人（code owner）团队列为请求评审人的拉取请求。我通常会省略 `review:required` 这个搜索限定符，因为即使同事已经评审过了，我也有兴趣再看一遍。毕竟，评审代码不仅帮到作者，也帮我随时了解影响我负责的代码的改动。

### 用评审团队管理通知

你不会希望代码改动去惊动一个太大的团队，以至于团队里每个人都认为评审这个改动不是自己的责任。这会带来两种结果：拉取请求无人理睬、迟迟得不到评审，或者在本该合并之前就被合并了——因为关键评审人被海量通知淹没，错过了它。这两种情况都会影响产品质量。

如果条件允许，我建议精简你所属的代码负责人团队数量，让通知量保持在可管理的范围内。这样一来，落到你收件箱里的拉取请求就不只是噪音，而是你真的觉得应该去评审的东西。大而全的代码负责人团队作为兜底选项还行，但作为自动评审请求的第一道默认选择并不理想。把仓库的 CODEOWNERS 文件整理好，配合清晰划定的代码边界，这样既能限制通知量，也能帮评审人避免通知疲劳（notification fatigue）。

另一种限制团队通知的办法，是建立一个第一响应人（first responder）团队，然后用自动化按排班增删团队成员。这样你的团队可以专注于日常维护的代码库，而排到班的第一响应人负责接收团队服务范围内拉取请求的通知。比如，用 PagerDuty API 可以确定某一天谁是第一响应人，然后用 Octokit 库来增删团队成员。

### 用自动化统一跨团队的评审标准

仓库级别的配置和自动化——比如使用 CODEOWNERS 文件和分支保护规则——有助于在各团队间强制执行评审流程标准。而另一些标准，比如拉取请求里哪些地方值得评论，只能靠我们人来维护。把你团队内部代码评审的运作方式写进文档，确保每个做代码评审的人、每个提交拉取请求的人都知道：怎么让自己的拉取请求得到评审、预期的评审周转时间是多久、以及有哪些自动化在辅助评审。

有些团队用项目看板来跟踪有哪些拉取请求进入评审；我看到这对管理共享 API 的团队效果很好——这类模块经常被团队之外的人修改。另一些团队只依赖 GitHub 通知，我发现当代码归属范围划得很紧、团队又能严格做到拉取请求一到就评审时，这样效果也不错。

如果你采用的方法是你团队特有的，自动化可以帮你把预期传达给团队之外的人。比如，如果有很多其他团队依赖你们团队的评审，你可以用一个机器人，在任何请求你们团队评审的拉取请求上自动留言，告诉作者大概什么时候能得到回复。

## 什么样的代码评审是好，什么是坏？

好的代码评审增加清晰度，并把代码推向比它开始时更好的状态。

作为评审者，沟通清晰是关键。你要说清楚哪些评论属于个人偏好，哪些是批准前的阻塞项。为你建议的做法举一个例子，能提升这条代码评审的质量，也让你的意思更明确。如果你能从该拉取请求所在的同一个仓库里举例，那就更好了——这会通过鼓励实现方式的一致性，进一步支持你的建议。

相比之下，糟糕的代码评审缺乏清晰度。比如，一句评论都不写，只是笼统地批准或否决，会让拉取请求作者怀疑这次评审是否认真。哪怕你在批准时只是复述一遍你对作者意图的理解，也能暴露出你和作者的理解是否一致。

如果一次代码评审没说清它的建议该在什么时候落实，作者的体验也会很差。指出已有、未改动的代码应该重构，或者某个额外情况应该处理，这些都没问题，但重要的是说明这些是不是批准的前置条件。如果这个拉取请求不做你的建议也可以合入，务必明说。把差异（diff）保持得小一些、把这些改动拆成单独的拉取请求分别交付，可能更稳妥。

下面这条代码评审评论，既具体，又清楚地传达了建议的做法：

「我看到你新增的方法沿用了这个文件里已有的风格，接收 [X] 个参数。参数这么多会损害可读性，也说明这个函数做的事情太多了。你觉得在后续的拉取请求里，把这个方法和已有的方法一起重构、减少参数数量怎么样？」

这条评论做得好的地方：

- 给出了具体的细节。
- 引用了具体的代码或问题。
- 提出了问题的解决办法。
- 引用了证据或给出了解释。

反过来看，下面是一些本可以写得更好的评审评论示例：

**「我不喜欢这个。」**——评论者不喜欢什么？他心里有没有一个可以明说的替代方案？

可能的改进：

- 「这一行做的事情太多了，能不能简化一下，提升可读性？」
- 「我觉得这会有性能问题，因为是个 n+1 查询。」
- 「这里能不能用 [preferred framework] 自带的方案，而不是自己写一套实现？」

**「这样不行。」**——为什么这些改动不行？

可能的改进：

- 「这样不行，因为 [X]，看这个相关问题：[issue link]。」
- 「之前在 [pull request link] 里试过，因为 [X] 没成功。」
- 「如果你在 [X] 上遇到问题，可以改用 [alternative approach]。」

**「我觉得这修了一个 bug。」**——我很喜欢这种点名，但能不能补充点上下文，比如一个 issue 链接，让它更清楚？

可能的改进：

- 「我觉得这修好了 [issue link]。」
- 「这是在修 [issue link] 里的那个 bug 吗？」
- 「这看起来就是我们在 [link to failing build] 里遇到的那个 bug。谢谢修复！」

## 如何给出好的代码评审

### 多提问

我把拉取请求作者看作最了解这次改动背景的人。我可以根据我的经历——在 Ruby on Rails 单体应用里、在 TypeScript 里、或者在高流量数据库上的经验——指出我看到的问题，但我相信我提问后作者给出的回答。我认定他们对具体细节的理解比我更准确。

我也很喜欢就代码里的假设提问。他们处理的数据是什么形状？有没有不符合这个形状的数据存在？代码能妥善应对吗？这段代码吃资源吗？性能会好吗？作为评审者，我最喜欢的回应是作者提供一个自动化测试，验证这些场景下的行为。第二喜欢的回应是实证数据，比如一条来自我们数据仓库的查询，或者一张 Datadog 图表，说明为什么这些场景不是问题。

作为拉取请求作者，我很欢迎收到问题。有人提问，就给我留出了空间，去解释我为什么对这次改动有信心，必要时引用 issue、查询或图表。这也让我能把自己的知识和经验分享给别人。我的回复不只有作者能看到，其他评审者、以及将来想弄清某个历史决策背景的人也能看到。

### 给出肯定

除了提问，对拉取请求里你认同的部分发表评论也是个好习惯。这类评论能表明你读懂了正在改的东西，或者你验证了代码里的某个假设。举几个例子：

- 「看起来这和本模块其他类用的模式一致。」
- 「谢谢你为这个加了测试！」
- 「这比之前可读性好多了。」

就我的经验而言，收到这类评论本身也让人舒服。收到代码评审有时会让人心力交瘁。当我面对来自好几方的提问和建议时，收到几条不向我索取任何东西、只是支持和认可我已经付出努力的评论，会是很大的鼓舞。

### 留意偏见和预设

你对评审者的偏见，或者对对方正在改的这块代码的偏见，很容易影响你的评审。你会习惯某个人在某个模块工作、或者有某个资历级别，就默认他清楚自己在做什么——但每个人都会犯错。你去看他的改动，用你的问题去检验他的假设、也检验你自己的假设，就能在上线之前抓出问题。

> 译注：原文此处为 "your biases about the reviewer"，但结合上下文看，指的应是**被评审的作者**，疑似原文笔误；此处照原文直译。

我非常推崇写测试，因为测试能去掉一部分偏见。当你写测试来检验代码是否正常工作时，你不需要相信作者的口头保证，只要看测试是否通过——前提当然是你这个测试本身写对了。😅

我也非常推崇初级开发者在代码评审里向资深开发者提问，哪怕他们觉得自己的问题很傻、或者答案很明显。如果对你来说不明显，那你的困惑就是合理的。对别人来说它也不会明显！把问题问出来，给作者留出写下回答的空间，也把这一点点知识留给后来的人。

### 批还是不批

我把自己的评审看作一道拦截闸门，它可能挡住别人改进我们的产品，所以我扣着不批时是很慎重的。我经常会有个人偏好，也会建议作者做哪些可选的改动，但我不会仅仅因为这些就不给批准。如果我对某个人的拉取请求有建议，但按它现在的样子并不会搞坏生产环境、不会对用户造成负面影响、也不会引发其他问题，我就会带着这些评论批准。作者可以选择在合并之前处理我的反馈，也可以另开一个分支后续跟进。

评审代码时，要掂量一下你这条建议的分量。为了让建议被采纳而推迟交付，值得吗？让作者走完整个循环——看到你的反馈、做建议的修改、等 CI、再评审、部署、最后合并——值得吗？如果少了一条建议并不会让谁的日子更难过，那就让作者自己决定要不要改、什么时候改。

「请求修改」（Request changes）这个选项会阻止拉取请求被合并，直到评审者回来批准它。我极少用它，因为它通常显得太强硬。我相信我的团队知道什么时候该批准一个拉取请求，所以同事的批准可以代替我的。同样，我相信拉取请求作者会尊重并考虑我的反馈，而不是因为别人批了、我没批就盲目合并。我唯一会选「请求修改」的时候，是我认为存在紧迫的安全问题、担心他们在合并前看不到我的顾虑。

## 如何从代码评审中获得最大收益

### 评审自己的代码

GitHub 资深软件工程师（Senior Software Engineer）Paul Smith 教我在请别人评审之前先评审自己的拉取请求，我也建议你这么做。先过一遍，对那些不明显、或者如果出现在别人的拉取请求里你一定会问的改动，直接在行内留言。自我评审还能帮你判断一个拉取请求是不是太大了、拆开来会更好。

特别推荐：如果你在意让自己的拉取请求保持小巧，可以用 `lerebear/sizeup-action`，它会自动给拉取请求打上标签，标明其复杂度和大小。

### 欢迎合并后的评审

如果我碰巧在别人来得及评审之前就把拉取请求合并了，我依然欢迎他们的评审。如果我的拉取请求弄坏了什么，或者有预料之外的后果，在拉取请求上留言就留下了面包屑痕迹，帮后来的人弄清当时发生了什么！

如果我在一个已经合并的拉取请求上收到评审，我会像在它合入之前那样处理这些反馈。可能是一条解释我看法的评论，可能是再开几个拉取请求、对最初交付的代码继续迭代。也可能是新开几个 issue，把待办的工作记录下来。

### 使用草稿拉取请求

新建拉取请求时，你可以选择把它设成草稿。我非常依赖草稿状态来表达我到底要不要评审。比如，某个必需的 CI 构建失败了，或者我还没做完，我就会让它保持草稿状态。我对别人的拉取请求也倾向于同样对待：如果是草稿，我就默认作者还没准备好接受评审。如果标记为「可评审」，我就默认他们只差拿到足够多的批准就能部署这个拉取请求了。

草稿状态意味着拉取请求还没完成，所以在解决合并冲突或处理评审反馈时，我会把拉取请求改回草稿。如果我必须改动代码，我会先把拉取请求标成草稿，免得打扰那些已经评审过的人。等我把它改回「可评审」时，GitHub 会给那些评审者发通知，让他们再看一遍。

### 保持风度

我想到一句老话：「用蜂蜜比用醋能抓到更多苍蝇。」我希望自己的拉取请求有人来评审，所以我喜欢回复自己拉取请求上的评论——尤其是我不同意评审者意见的时候。即使我不写回复，我也常常用 👍 表示同意，或者用 ❤ 表示感谢。

我希望评审者相信他们的建议不会被遗忘，所以我会通过评论让他们保持知情。如果我同意他们的建议——比如进一步重构现有代码——我可能会这么说，同时也反对在当前这个拉取请求里做这个改动。等我在后续的拉取请求里处理了他们的反馈，我会回来贴个链接，让评审者知道他们的反馈没有被当作耳旁风。

在后来实现这些建议改动的拉取请求里，我也会 @ 他们，并附上一句「这处理了 @某某 在 <上一个拉取请求的 URL> 中提出的反馈」。这既为其他读者提供了背景，也是对原评审者的一次点名致谢，把功劳记给他们。

当你兑现了「稍后分支里处理反馈」的承诺，这会帮助你和评审者建立信任，让他们更放心地批准你以后的拉取请求，因为他们知道你不会把事情做一半就丢下。

## 小结

代码评审对产品质量的重要性怎么强调都不过分，在 AI 生成代码的时代尤其如此。在我的职业生涯里，有很多次，仅仅因为多了那一双眼睛，就抓出了一个 bug 或避免了一次事故。代码评审非常值得投入时间，无论是花在日常评审上、花在理顺流程上，还是花在构建支持评审的自动化上。对开发者来说，现在把拉取请求评审透彻，比以后去处理一个已经发到生产环境的问题更快、也更少痛苦。

谢谢你如此在意代码质量，读完了我关于代码评审的理念。你最近看过自己的评审队列吗？也许现在正是把这些想法付诸行动的好时机。

如果你想进一步了解如何在 GitHub 上使用拉取请求评审，可以看看 GitHub Community 上的一篇文章，由资深 DevOps 架构师（Staff DevOps Architect）Mickey Gousset 与资深 DevOps 架构师（Staff DevOps Architect）Joshua Johanning 撰写的《评审拉取请求的 5 个技巧》（5 Tips for Reviewing a Pull Request）。
