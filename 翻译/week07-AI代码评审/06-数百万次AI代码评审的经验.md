**演讲原题**：AI powered entomology: Lessons from millions of AI code reviews
**演讲者**：Tomas Reimers，Graphite 联合创始人

## 开场：AI 到底能不能找 bug

非常感谢大家来听这场演讲。也谢谢大家来到这次大会。

我叫 Tomas，是 Graphite 的联合创始人之一，今天想跟大家聊聊 AI 驱动的昆虫学（AI-powered entomology）。如果你不知道的话，昆虫学研究的是虫子（bug）——这件事跟我们的关系非常密切，也是我们产品在做的事情之一。

Graphite 这家公司，不了解的人可能不知道，我们做了一款产品叫 Diamond。Diamond 是一个 AI 驱动的代码评审器。你把它接到自己的 GitHub 上，它就会去帮你找 bug。

这个项目大概是一年前启动的。我们开始注意到，AI 写的代码量在涨、涨、涨，但 bug 的数量也在涨。认真想了想之后，我们觉得这两件事可能本来就是一体两面，而我们需要做的，是找到一种办法，从整体上更好地应对这些 bug。

考虑到技术的进步，我们首先求助于 AI 本身。我们开始问：也许 bug 是 AI 造出来的，那它能不能也把 bug 找出来？它能不能帮上忙？

于是我们开始做这样的事：把 Claude 叫过来，「嘿，这是一个拉取请求（PR），你能在这个 PR 上找出 bug 吗？」我们对早期结果相当满意。

这里有一个例子，其实就是本周从我们自己的代码库里翻出来的：在某些情况下，我们会返回一个没有实例化的数据库 ORM 类，这会直接把我们的服务器搞崩。

还有一个例子是本周出现在 Twitter 上的，来自我们的机器人：在某些情况下，围绕 border radius（边框圆角）做的数学运算会导致除以负数，进而把前端搞崩。

所以，回答最开始那个问题：事实证明，AI 能找出 bug。演讲到此结束。

开个玩笑。如果你试过这件事，你就知道你大概经历过非常非常令人沮丧的体验。

我们也看到过这样的东西：「你应该把这段代码改成它现在就已经在做的事。」「CSS 不是这么工作的」——可它就是这么工作的。还有我最喜欢的一条：「你应该把这段代码改回它原来的样子，因为它原来就是那样做的。」

收到这些让我们信心大减。但我们开始想：我们既看到了很好的东西，也看到了很糟的东西，那也许 bug 不止一种类型，大语言模型（LLM）能找出来的东西也不止一种类型。

## 不只是「能抓」和「抓不到」两个类别

于是我们从最基础的划分入手：有些东西 LLM 擅长抓，有些东西它不擅长抓。归根结底，LLM 只是在试图模仿你让它做的事情。如果你问它「这个 PR 上会留下什么样的代码评审评论」，它就会把所有东西都留下——既包括它能力范围内的，也包括它能力范围之外的。

于是我们开始对这些评论分类。但我们发现，即便分了类，LLM 还是会留下这样的评论：「你应该加一条注释，说明这个类是干什么的。」「你应该把这段逻辑抽成一个函数。」或者「你应该确保这段代码有测试。」

这些评论技术上都没错，但对开发者来说，它们非常烦人。

我觉得这其实是我们在做这个项目时最有洞察力的时刻之一：我们和设计团队坐下来，真的去把过去的 bug 翻了一遍，既有我们的机器人留下的，也有我们自己代码库里人类留下的。

开发者们的看法几乎完全一致，就是那种「对，LLM 留这条我没问题」「不，LLM 留这条我有问题」「对，这条可以」。而我们的设计师对此其实相当困惑。他们说，可是这看起来跟那条评论差不多啊。

我觉得这里发生的事情是，在开发者的心里：如果你读到这样一条评论，当它来自 LLM 时，你可能会觉得它迂腐、烦人、讨厌；而当它来自人类时，你就要欢迎得多。

所以，当我们开始更多地思考 bug 的分类时，我们开始想到其实是第二个维度：有些东西 LLM 能抓、有些抓不到，但也有一些人想从 LLM 那里收到、另一些人不想从 LLM 那里收到。

> 译注：此处转写作 "second access"，按其上下文（与下文的象限划分对应）应为 second axis，即「第二个维度」。

## 拿 10,000 条评论来做分类

于是我们做的是：我们从自己的代码库、从开源代码库里拿出了 10,000 条评论，把它们喂给各种 LLM，让它们给这些评论分类。而且我们不是只做了一次，我们做了相当多次。然后我们把这些评论汇总起来，最后得到的就是这张图。

图上显示，在真实世界的代码库里，你看到的评论其实有相当多种不同的类型。先不管 LLM，只说人类：你会看到 bug——就是那些逻辑上的不一致，导致代码的行为不是它想要的行为。还有误提交的代码，这个出现的频率比你想的要高。有性能和安全隐患。有文档问题：代码说的是一回事，做的又是另一回事，而且看不出哪个才是对的。有风格上的修改，比如「嘿，你应该更新一下这条注释」，或者「在我们这个代码库里，我们用的是另一种写法」。

## 四个象限：人想收的 vs. LLM 给得出的

然后还有大量东西落在右上象限之外。

在右下角——也就是人类想收到、但 LLM 目前似乎还够不着的地方——是「部落知识」（tribal knowledge）这类东西。你在 PR 里会经常看到一类评论：「嘿，我们以前是这么做的，后来因为某某原因不这么做了。」这种文档是不存在的，它只存在于资深开发者的脑子里。这很好，但要让 AI 去读心，真的很难。

在左边——LLM 肯定能抓到、但人类不想收到的地方——就是我前面给你看的那些东西：代码整洁度和最佳实践。我们找到的例子包括：「给这个函数加注释」「加测试」「把这个类型抽成另一个类型」「把这段逻辑抽成一个函数」。这话说出口永远是对的，但我觉得，真正难的是知道什么时候该对 LLM 说。

我觉得作为人类，你在应用某种标尺：「在这个代码库里，这段逻辑特别容易让人栽跟头，所以我们应该把它抽出来」；而换一个代码库，「其实这样挺好」。但机器人几乎永远都可以留这条评论。我甚至会说，人类也几乎永远都可以留这条评论，而且技术上都是对的。问题在于，它在代码库里欢不欢迎。

我想说一点，某种程度上在这些之外：随着你加入更多东西，人们能接受的这块区域看起来会变大。但就目前而言，考虑到我们手上的上下文、考虑到代码库、过往历史、你的风格指南和规则，我们有什么就用什么。

于是我们得出了这样一个想法：归根结底，这些就是我们认为 LLM 既能产出、人类又愿意收到的评论类别。

## 怎么持续知道自己做对了

现在，如果你跟 LLM 打过交道，你就知道这种离线跑一遍、先跑一遍的做法，很适合做初步分类；但难得多的问题是：你怎么知道你是持续做对的？

所以故事是这样的：我们开始给 LLM 留下的评论做特征刻画，然后更新我们自己的提示词，只让 LLM 去做它能力范围之内、而且人类愿意收到的事情。从大家的反馈看，他们开始喜欢得多了。

但当我们接着想「我们怎么知道这件事在往对的方向走」——当我们考虑新的 LLM，比如从 Sonnet 换到 Claude 4 或 Opus 的时候，我们怎么知道自己还真的待在这个右上象限里？当我们把上下文加长的时候，我们怎么知道这个象限没有反过来把我们吞掉？而且实际上，也许还有更多类型的评论，是我们本来可以留、现在却没留的。

所以首先，我们做的第一件事，就是看它现在到底在留什么类型的评论。

你的结果可能会不一样。对我们来说，大致上这就是我们现在看到 LLM 留下的评论比例，仅仅基于我们观察到的数据。

但对我们来说更深的问题是：我们怎么衡量成功？给定这个象限，我们怎么知道自己在右上角？

第一个问题对我们来说比较简单。想想「它们能抓什么、抓不到什么」。我们开始做的是，在产品里加上点赞和点踩。我们让你可以对这些评论用 emoji 表态，它们基本能告诉我们 LLM 什么时候在幻觉——当我们看到点踩量飙升，就知道：好吧，我们可能是在把这个东西往它的能力边界之外推，得收一收了。

但第二个问题难得多。「人类想收到」和「人类不想收到」，这是我们不太确定该怎么着手的。

## 点赞、点踩，以及「评论有没有真的带来改动」

点赞、点踩我们做了，现在点踩率不到 4%，我们对此感觉还不错。

第二个问题，当我们开始琢磨它的时候，我们意识到的是：一条评论的意义是什么？你在代码评审里为什么留评论？归根结底，你留评论是为了让别人真的去改代码，把评论反映出来。

所以我们的问题是：我们能衡量这件事吗？我们能不能衡量，有多少比例的评论真的带来了它们所描述的那个改动？

于是我们开始做这件事。我们开始问这个问题：在开源仓库上，在 Graphite 这个代码评审工具能接触到的各种仓库上，我们能不能真的把这个数字量出来？

我觉得我们发现的最有意思的事情之一是：人类留下的评论里，只有大约 50% 带来了改动。

于是我们开始问：那我们能不能让 LLM 至少达到这个水平？因为如果能达到这个水平，那它留的评论至少是在人类能达到的保真度上。

现在，观众里可能有人会说：为什么不是 100% 的评论都带来行动？我想给这个数字加一个限定：我说的是「在这个 PR 之内」带来行动。

所以很多评论其实是「向前修复」（fix forward）的，人们会说「嘿，我听到了，我会在后续的改动里修掉」。还有很多评论是这种：「嘿，提醒你一下，以后如果你这么做，也许可以换个做法」——但它们并不需要被处理。还有一部分纯粹是偏好问题：「我会这么做」，而别人不同意。在健康的代码评审文化里，这种分歧的空间是存在的。

于是我们开始衡量这个指标。我们开始问：能不能把机器人做到这个水平？随着时间推移，我们确实做到了。到三月为止，我们到了 52%——也就是说，如果你真的把提示词写对了，你是能达到这个水平的。

## 结语

我想我们更宏观的论点是：用 LLM 找 bug，这件事确实是行得通的。

如果你想在生产环境里试试这些发现里的任何一条，Diamond 就是提供这个功能的产品。我们在那边有个展位。

谢谢。谢谢。谢谢。
