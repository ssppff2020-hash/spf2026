## 执行摘要

模型上下文协议（MCP）是一个开放标准，它把 AI 模型与外部数据和服务连接起来，让大语言模型（LLM）能够以一致、安全的方式进行结构化的 API 调用。本文将介绍 MCP，说明它为什么在连接 AI 系统方面很有价值，把它与 ChatGPT 插件、手工 API 集成等既有做法做比较，并深入探讨它近期对基于 OAuth 的认证的支持。我们还会看一点代码，看看 MCP 实际如何运作。

MCP 充当 AI 工具与外部服务之间的通用适配器，免去了为每个工具或 API 编写定制集成代码的需要。就像 USB-C 简化了各种设备之间的连接一样，MCP 为 AI 模型提供了统一的方式来调用外部函数、获取数据或使用预定义的提示词。归根结底，MCP 提供的是一套接口，去连接众多不同的系统。

## 什么是模型上下文协议 MCP？

MCP 本质上是 AI 应用与外部工具或数据源之间的通用适配器。它定义了一套通用协议（基于 JSON-RPC 2.0 构建），让 AI 助手能够以结构化的方式调用外部服务的函数、获取数据或使用预定义的提示词。有了 MCP，每个 LLM 应用不必再为每个 API 或数据库编写定制代码，所有交互都使用一种标准化的「语言」。

MCP 这一层让 AI 应用能够安全地访问外部数据源和工具并与之交互。它充当大语言模型（LLM）与各种数据库、应用或 API 之间的桥梁，无需大量定制编码就能实现无缝集成与功能对接。

MCP 采用客户端-服务器架构来实现这一点。由 AI 驱动的应用（例如聊天机器人、IDE 助手或智能体）充当宿主，运行一个 MCP 客户端组件；而每一个外部集成则以 MCP 服务器的形式运行。服务器通过 MCP 协议暴露各种能力（如函数、数据资源或提示词模板），客户端连接它来使用这些能力。这种分离意味着 AI 模型不直接与 API 对话，而是经过 MCP 客户端/服务器的握手，由它来组织数据交换。

## MCP 为什么有价值

在传统做法中，把 AI 模型连接到外部数据或操作既繁琐又临时凑合。开发者常常得为模型想要使用的每个 API 或数据库写一次性的集成，还要分别处理各自的认证、数据格式和错误处理。MCP 通过标准化这些交互改变了局面。主要好处包括：

**快速集成工具（Rapid Tool Integration）**：有了 MCP，你可以直接接入新能力，而不必从零为每一个定制编码。如果某个服务——比如说 Google Drive 或某个 SQL 数据库——已经有现成的 MCP 服务器，任何兼容 MCP 的 AI 应用都能连上它并立刻获得这项能力。这对自动化来说是巨大的胜利——AI 智能体只要挂上相应的服务器，就能按需获取文档、查询数据库或调用 API。这就像拥有一个现成的「插件」库，所有插件都说同一种语言。MCP 服务器是轻量级程序，通过标准化协议暴露特定能力，充当 Cursor 与各种外部工具或数据源之间的中介。

**自主智能体（Autonomous Agents）**：MCP 让 AI 的行为更加自主。智能体不再局限于自身内置的知识，它们可以在多步工作流中主动获取信息或执行操作。例如，一个复杂的智能体可以用 MCP 从 CRM 收集数据，然后通过通信工具发一封邮件，再在数据库里记录一条日志——全程一条无缝的链路。通过促成流畅的、具备上下文感知的多步交互，MCP 让 AI 智能体更接近真正的自主任务执行。正如一位观察者所说，MCP 通过赋予 AI 对现实世界工具和数据的标准化访问，把 AI 从一个孤立的「大脑」变成了多才多艺的「执行者」。

**减少摩擦与配置（Reduced Friction and Setup）**：因为 MCP 充当通用接口，开发者不必再陷于维护各种独立集成的碎片化之中。一个应用一旦支持 MCP，就能通过单一机制连接到任意数量的服务。这大幅减少了每次想让 AI 使用新 API 时所需的手工配置。团队可以把精力放在更高层的逻辑上，而不是第十次重新发明连接代码。正如 Anthropic 所说，MCP 用一套更简单、更可靠的数据访问协议取代了碎片化的集成。

**一致性与互操作性（Consistency and Interoperability）**：MCP 在各类工具之间强制统一请求/响应格式。这意味着你的 AI 应用不必为服务 A 处理一种 HTTP 响应、为服务 B 处理另一种 XML，等等。模型的输出（函数调用）和工具结果都通过统一的 JSON 结构传递。这种一致性让调试和扩展都更容易。它也让你的集成逻辑面向未来——即使你更换底层模型厂商，MCP 与工具之间的接口依然不变。

**双向上下文（Two-Way Context）**：与简单的 API 调用不同，MCP 支持在模型与工具之间维持上下文和持续对话。除了工具，MCP 服务器还可以提供 Prompts（针对特定任务的预定义提示词模板）和 Resources（文档之类的数据上下文）。这意味着 AI 不仅能「调用 API」，还能摄取参考数据，或遵循由服务器引导的复杂工作流。该协议在设计上就是为了支持丰富的交互，而不只是一次性查询。这在编程助手之类的应用中尤其有用（AI 可以通过 MCP 与开发环境反复交互），也适用于需要与多种数据源来回沟通的复杂决策任务。

简而言之，MCP 为增强 LLM 带来了一种可扩展、即插即用的方式。它让 AI 系统能安全地接入它们所需的「实时」数据和操作，而不必每个开发者都去重复造轮子。MCP 的早期采用者已经为 Google Drive、Slack、GitHub、数据库等工具构建了服务器——这展示了 AI 智能体如何借助 MCP 与企业内容仓库、DevOps 工具以及其他现实世界系统协作。

## MCP 架构 —— 一眼看懂它如何运作

### 客户端-服务器结构

MCP 遵循清晰的客户端-服务器架构：

**MCP 客户端**：内嵌在 AI 应用（聊天机器人、IDE 助手、自动化智能体）中。

**MCP 服务器**：暴露外部能力，例如函数（工具）、资源（数据）和提示词（模板）。

所有交互都通过标准化的 JSON-RPC 消息进行，保持安全、结构化的交换：

示例 JSON-RPC 请求：

例如，要列出可用的工具，MCP 客户端会发送这样的请求：

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "tools/list",
  "params": {}
}
```

这是一次 `tools/list` 请求，用来向服务器索取可用工具的清单。

服务器会用一段结构化的 JSON 回复，列出这些工具（每个工具都带名称、描述和输入 schema）。例如，服务器可能提供一个 `get_weather` 工具，并说明它需要哪些输入。

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "result": [
    {"name": "get_weather", "description": "Retrieves weather data.", "schema": {"location": "string"}}
  ]
}
```

之后，当 LLM 决定使用某个工具时，客户端就发起一次调用。MCP 服务器执行该函数，并以结构化的 JSON 响应返回结果。MCP 客户端（位于宿主应用内）再把结果送回模型的上下文或回复中。在实践中，宿主应用负责居间协调这一过程：它把 LLM 的意图（通常是模型的函数调用输出）翻译成一次 MCP 请求，再把服务器的结构化结果传回 LLM。这种双向交换既安全又受控——模型只能调用服务器暴露的那些特定工具，所有进出的数据都要经过既定协议。

## 构建与部署 MCP 服务器

构建和部署 MCP 服务器是利用模型上下文协议（MCP）做 AI 集成的关键一步。MCP 服务器充当 AI 模型与外部数据源或工具之间的中介，实现无缝通信与数据交换。MCP 的一个突出特点是服务器开发的灵活性。开发者可以使用任何能向 stdout 打印输出或提供 HTTP 端点的编程语言，从而自由选择自己偏好的语言与技术栈。

构建 MCP 服务器时，必须考虑架构与设计。MCP 遵循客户端-服务器架构，一个宿主应用可以连接多个服务器。这种架构带来可扩展性与灵活性，让开发者可以设计处理各种任务和功能的 MCP 服务器，例如数据处理、工具集成或 AI 模型管理。

MCP 服务器可以部署在各种环境中，包括本地开发环境、云平台或本地自建基础设施。例如，Cloudflare 提供了用于构建和部署远程 MCP 服务器的稳健平台，让 MCP 部署更易于管理和扩展。这种灵活性确保 MCP 服务器能按不同应用和环境的特定需求量身定制，无论是用于开发的本地部署，还是用于生产的云端方案。

关注良好的架构设计并善用 MCP 的灵活性，开发者就能打造强大且可扩展的 MCP 服务器，增强 AI 模型的能力，使其能与外部数据源和工具无缝交互。

## MCP 客户端与工具

MCP 客户端与工具是模型上下文协议生态的重要组成部分。MCP 客户端是连接 MCP 服务器、以访问外部数据源或工具的应用。这些客户端可以用 Python、JavaScript 或 Java 等各种编程语言和框架来构建，让开发者能灵活选择最适合自身需求的工具。

而 MCP 工具则是为 MCP 客户端提供特定能力或功能的软件组件。这些工具可以与 MCP 服务器集成，实现数据处理、AI 模型管理或工具集成等特性。MCP 工具的例子包括 Claude Desktop（提供与 AI 模型交互的聊天界面）和 Cursor（提供扩展 AI 能力的插件系统）。

开发者可以构建自定义的 MCP 客户端和工具，以满足特定的用例或需求。这种灵活性为 MCP 生态带来创新与试验的空间，让开发者能创造出新颖而精彩的应用。无论是用于数据分析的专用工具，还是能集成多个 MCP 服务器的客户端应用，可能性都非常广阔。

借助 MCP 客户端与工具，开发者可以打造稳健而多用途的应用，充分释放 AI 模型的潜力，让它们能与广泛的外部数据源和工具无缝交互。

## 把 MCP 与其他做法做比较

| | MCP | 自定义集成 | ChatGPT 插件 | LangChain 及框架 |
|---|---|---|---|---|
| **集成速度** | ✅ 快，即插即用 | ❌ 慢，需要定制代码 | ⚠️ 中等，专有 | ⚠️ 中等，需要定制代码 |
| **认证** | ✅ OAuth 标准 | ❌ 手工管理 API key | ⚠️ 插件专属 OAuth | ❌ 因实现而异 |
| **交互类型** | ✅ 持续且上下文丰富 | ❌ 临时性交互 | ❌ 单次交互 | ⚠️ 上下文受限 |
| **开放标准** | ✅ 是 | ❌ 否 | ❌ 否 | ⚠️ 依赖特定框架 |

我们来比较几种在 MCP 之前或与之同时存在的做法：

**自定义集成与 API 密钥管理**：最常见的传统做法是为每个服务编写定制代码，并把凭据（API key 或 token）交给 LLM 去使用那些集成。例如，你可能会写一个 Python 函数来查询某个 API，让 LLM 有能力调用这个函数，并在后端手工处理 API key。这种做法劳动密集且无法规模化——每新增一个数据源就要写新代码，每个环境都必须安全地管理 API key。它往往导致系统脆弱，因为每个集成都是独一无二的。相比之下，MCP 把这些交互集中并标准化：AI 智能体只需处理 MCP 协议，任何（面向任何服务的）MCP 服务器都能即插即用。新增服务器完全不需要改动客户端的代码。此外，MCP 还提供了正式的认证结构（后文会讲），这样把 API key 交给 AI 就不再是临时凑合，而是通过安全协议完成。

**ChatGPT 插件（OpenAI 插件）**：2023 年，OpenAI 为 ChatGPT 引入了一套插件系统，允许模型调用由 OpenAPI 规范定义的外部 API。这是通向标准化工具调用的早期一步，但它有局限。每个插件本质上都是自己的小型集成（有自己的 API schema 和认证），需要单独构建和托管。由于这是专有做法，只有特定平台（如 ChatGPT 或 Bing Chat）能使用这些插件。插件也大多是一次性调用——模型调用一个 API 拿到信息，没有持久连接或持续交换。MCP 的不同之处在于它是开放且通用的（不绑定某个厂商或界面），并且支持丰富的双向交互与持续上下文。可以把 ChatGPT 插件看作封闭工具箱里的专用工具，而 MCP 是任何开发者或 AI 平台都能使用的开放标准工具箱。MCP 标准化的认证（尤其是 OAuth）也意味着，它能以比 ChatGPT 系统里逐个插件走 OAuth 更统一的方式，处理对用户数据的安全访问。总结一下，ChatGPT 插件展示了为 LLM 标准化 API 访问的价值，而 MCP 更进一步，把它变成开放协议，并让 AI 与服务之间能够持续「对话」。

**LLM 工具框架（LangChain、智能体类库）**：在 MCP 之前，许多开发者用 LangChain 之类的框架给模型配上工具。在这类做法里，你定义一组工具函数（带描述）以及智能体的提示逻辑，让 LLM 能决定使用它们。这行得通，但每个工具背后仍然需要定制实现——LangChain 最终在它的库中维护了数百个工具集成。本质上，LangChain 提供了一个面向开发者的标准（一个 Python 类接口），用于把工具集成进智能体的代码库，但没有给模型提供在运行时动态发现新工具的能力。MCP 与这些框架是互补的，它把标准化转向面向模型。有了 MCP，智能体可以发现并使用任何 MCP 服务器提供的工具，即使智能体的代码事先没有显式包含那个工具。事实上，LangChain 已经添加了支持，可以把 MCP 服务器当作又一个工具来源——也就是说，用 LangChain 构建的智能体能轻松调用 MCP 工具，从而利用不断壮大的 MCP 服务器生态。区别在于，MCP 把接口形式化为一种协议（JSON-RPC，带元数据等），使其更容易接入不同的环境，而不只是 Python 框架。类似地，OpenAI 原生的函数调用特性可以看作处理函数调用的格式化（模型输出一个 JSON 函数调用），而 MCP 以标准化的方式处理这个调用的执行。OpenAI 的函数调用与 MCP 常常协同工作：LLM 产生结构化调用，MCP 客户端/服务器执行它并返回结果，二者合起来实现了无缝的工具调用。

本质上，MCP 并不是第一次尝试把 LLM 与外部 API 连接起来——但它从那些过往做法（插件、工具库等）中吸取经验，并把方案统一起来。它提供了一个开放、与模型无关的协议，简化了集成与认证。尤其在安全与认证方面，MCP 的设计（支持 OAuth）避免了每个插件各搞一套密钥的拼凑做法，也避免了把裸 API key 交给模型。相反，认证可以作为协议的一部分，以一致、标准化的流程来处理——相比现状是很大的进步。

## MCP 实战：技术深入

我们逐步走一遍典型的 MCP 交互，以巩固对它的理解，并看一点代码。假设我们有一个 AI 助手，它想使用某个提供一组工具的 MCP 服务器（比如说，为一个假想的「Neon」数据库服务）。高层流程如下：

1. **连接到 MCP 服务器** —— 宿主应用（AI 助手）初始化一个 MCP 客户端，并与服务器建立连接。视服务器位置而定，这可能是通过本地进程（stdio），也可能是远程 HTTP 流（SSE）。在底层，客户端会发送一条 `initialize` 消息，用于握手协议版本与能力。

2. **发现可用的工具/资源** —— 客户端接着查询服务器提供什么。如前所示，它可能发送 `{"method": "tools/list"}`，并拿回一份工具定义列表。助手可以用它来告知 LLM（例如把工具列表放进系统提示词，或通过模型的函数 schema 提供，取决于具体实现）。比如用 SDK，这可能只是一行代码，像这样：

```javascript
const tools = await mcpClient.request({ method: 'tools/list' }, ListToolsResultSchema);
```

它返回一份结构化的工具列表。每个工具条目都有名称、描述和输入的 JSON schema，这样 AI 就知道自己能做什么。

3. **LLM 选择工具** —— 当用户向 AI 提出的问题需要外部操作时，LLM 会判断（通常借助提示工程或函数调用能力）应该使用某个工具。例如，用户问：「AAPL 股票的最新价格是多少？」LLM 看出它应该调用 `get_current_stock_price(company="AAPL", format="USD")`。宿主应用捕获这个意图（例如 OpenAI 的函数调用 API 会返回一个 JSON 格式的函数名和参数）。

4. **通过 MCP 调用工具** —— 客户端现在把带有所选工具名和参数的 `tools/call` 请求发给服务器。前面我们看过这样的 JSON 示例。在代码里，用 SDK 可能像这样：

```javascript
const result = await mcpClient.request({
  method: 'tools/call',
  params: { name: toolName, arguments: toolArgs }
}, CallToolResultSchema);
```

这会让服务器在其一侧执行该工具的处理函数。服务器可能会调用外部 API、执行数据库查询，或者做该工具封装的任何逻辑。结果（可能是简单值，也可能是复杂的 JSON 对象）会在 MCP 响应的 `result` 字段中返回。

5. **把结果返回给 LLM** —— MCP 客户端收到工具的输出。现在宿主应用可以把它整合回 AI 的回复中。在许多智能体方案里，常见的模式是把结果注入对话，然后让模型继续。例如，助手随后可能呈现：「AAPL 当前股价为 173.22 美元（USD）。」如果使用自动化循环，结果可以交给模型（也许作为一条系统消息追加到对话里，如「Result of get_current_stock_price: ...」），模型就能带着这个信息继续回答用户的问题。

下面是一个简化示例，展示如何使用 Anthropic 的 Claude（原生支持工具调用）在对话中调用工具并使用结果：

```javascript
// 1. Send user prompt to LLM with available tools context
const response = await anthropicClient.complete({
  prompt: "User: Can you list my projects?\nAssistant: ",
  model: "claude-3.5",
  tools: tools // list of tools from MCP server
});
for (const msg of response.messages) {
  if (msg.type === 'tool_use') {
    // 2. LLM decided to use a tool
    const { name, args } = msg;
    // 3. Call the tool via MCP
    const toolRes = await mcpClient.request({ method: 'tools/call', params: { name, arguments: args } });
    // 4. Inject tool result and resume LLM
    await anthropicClient.send({ role: 'system', content: `Tool result: ${toolRes.result}` });
  } else {
    // 5. Handle normal LLM reply (tool result likely integrated)
    console.log("Assistant:", msg.content);
  }
}
```

现实中，框架会替你处理其中很大一部分，但上面的伪代码勾勒出 MCP 如何嵌入这个循环。关键在于，MCP 为工具执行提供了标准化的调用/响应层，AI 智能体代码可以挂接进去。不管你用的是 OpenAI、Anthropic 还是别的 LLM，MCP 都一样——它是模型意图与外部操作之间的黏合剂。

使用 MCP，开发者获得了一条清晰、结构化的流水线来扩展 AI 能力。代码变得更好维护（因为你调用的是通用的 `mcpClient.request`，而不是在每个地方写服务专属代码），AI 也变得更强（因为它能接入任何接入 MCP 的服务）。调试也更容易——你可以监控 JSON-RPC 消息，精确看到请求了什么、返回了什么，而不必从模型生成的文本里找线索。

## 早期局限（没有内置认证）

MCP 刚出现时（2024 年末），它提供了工具与数据交换的核心协议，但缺少连接远程服务器所需的标准化认证机制。实践中，早期的 MCP 演示和实现往往要求把 MCP 服务器运行在本地或可信环境中，那里认证不是什么大问题（因为 AI 和服务器跑在同一台机器上）。例如，开发者可以在 localhost 上用一个预先获取的 token 运行 Google Drive 的 MCP 服务器，然后让 AI 应用指向它。但如果没有正式的认证流程，在互联网上使用 MCP 或搭配第三方服务就很麻烦。

许多早期的 MCP 服务器假定用户会在启动时手工向服务器提供凭据或 API key。举个例子，Anthropic 的快速上手教程建议通过配置或命令行提供你自己的凭据（API key、token），来运行预构建的服务器。这意味着服务器本身能访问你的密钥，而 MCP 客户端只是信任那个服务器。这在个人或单用户场景下可行，但对于多用户应用或云端托管的智能体，就难以扩展。当时没有标准的握手方式让 AI 智能体说：「嘿，我获准代表用户 X 访问这项服务；这是我的凭据。」

本质上，早期的 MCP 客户端除了带外方式（比如预先共享一个 token，或者干脆不带认证运行）之外，没有别的办法向 MCP 服务器做认证。这是一个明显的局限——MCP 的设计初衷是开放、基于互联网的，但缺少认证标准让安全的远程使用受到了制约。

缺少认证标准意味着 MCP 客户端无法自行安全地连接任意服务器。你要么把 client ID/API key 硬编码进客户端（这在分布式应用里并不理想），要么只能不带认证运行，并假设只有获授权的用户才够得着服务器（通常靠把它保持在本地）。显然，要让 MCP 发挥全部潜力（例如让 AI 智能体安全地连接云端托管的数据源），需要更好的方案。好消息是社区认识到了这一点，并做了工作把基于 OAuth 的认证内置进 MCP。

### OAuth 2.0 认证流程

为解决最初的认证局限并增强安全连接，MCP 采用了 OAuth 2.0——一个被广泛认可且稳健的认证标准。OAuth 2.0 提供安全、可扩展的框架，让 MCP 客户端能够安全地与远程服务器、云端托管资源和多用户环境交互。把 OAuth 2.0 集成进 MCP 的关键组件与好处包括：

**动态客户端注册（Dynamic Client Registration，DCR）**：模型上下文协议支持动态客户端注册，允许客户端自动向 OAuth 服务器注册。这免去了手工配置客户端或硬编码凭据的需要，大幅简化了开发者的部署工作。

**自动端点发现（Automatic Endpoint Discovery）**：MCP 利用标准化元数据 URL（遵循 OAuth 的发现协议），让客户端能自动发现 OAuth 端点。这减少了配置开销，让 MCP 部署更容易、更灵活。

**安全的授权与 token 管理（Secure Authorization and Token Management）**：客户端安全地获取 OAuth token，这些 token 精确对应到用户权限和访问作用域。这确保客户端只能访问用户明确许可的资源，提升了安全性与合规性，在多用户和云环境中尤其如此。

**可扩展且安全的多用户支持（Scalable and Secure Multi-User Support）**：OAuth 2.0 的设计天然支持多个并发用户和服务，解决了 MCP 早期的一大局限。应用现在可以同时无缝处理大量用户的授权流程，这对云端的广泛采用至关重要。

## 调试与排查

调试与排查是使用 MCP 服务器和客户端时的关键环节。MCP 提供了多种调试与排查的工具和技术，确保开发者能高效地定位和解决问题。其中一个关键工具是 MCP Inspector，一个面向 MCP 服务器的交互式调试工具。

MCP Inspector 让开发者能够测试和检查 MCP 服务器，定位并解决 MCP 服务器集成中的问题。这个工具提供 MCP 客户端与服务器之间交互的详细视图，让定位问题和理解根本原因变得更容易。此外，MCP 还提供了一份全面的调试指南，列出常见问题与解决方案，帮助开发者快速排查和解决问题。

调试 MCP 服务器时，必须考虑系统的架构与设计。开发者应找出造成问题的具体组件或模块，并使用 MCP Inspector 之类的工具来诊断和解决问题。采用系统化的调试方法并善用现有工具，开发者就能确保自己的 MCP 集成稳健可靠。

## MCP 的现实应用

模型上下文协议（MCP）在各行各业、各个领域都有各种现实应用。MCP 的主要用例之一是 AI 集成，MCP 在其中实现 AI 模型与外部数据源或工具之间的无缝通信与数据交换。

MCP 可以用在各种应用中，例如：

**构建 AI 驱动的聊天机器人**：这类聊天机器人可以访问外部数据源或工具，为用户提供准确、最新的信息。

**创建 AI 驱动的工作流**：MCP 让 AI 模型能与外部系统或数据源集成，自动化复杂工作流并提升效率。

**开发 AI 模型**：这些模型可以与外部工具或数据源交互，增强自身能力，提供更准确、更相关的输出。

**实现 AI 驱动的自动化**：在金融、医疗或制造等行业，MCP 可以自动化任务与流程，提高生产力并减少错误。

MCP 的灵活性与适应性，使它成为希望在应用中利用 AI 和机器学习的开发者与组织的一个有吸引力的方案。通过为 AI 模型提供与数据源和工具交互的标准化接口，MCP 为 AI 生态带来创新与试验的空间。这种标准化做法不仅简化了集成过程，也确保 AI 模型能访问到它们发挥最佳表现所需的数据与工具。

总而言之，MCP 为 AI 应用打开了无限可能，让开发者能创建更集成、更自主、更可扩展的方案。无论是用 AI 驱动的聊天机器人提升客户服务，还是在工业场景中自动化复杂工作流，MCP 都提供了把这些创新落地所需的工具与框架。

## 结论

模型上下文协议（MCP）是 AI 开发中一个令人兴奋的进展，因为它让开发者能够安全、高效地把我们日益智能的语言模型连接到此前难以连接的广阔软件与数据世界。通过引入一套通用协议，MCP 让我们能构建更集成、更自主、也更容易扩展的 AI 系统。我们不必再为每个新工具编写一次性插件或给模型下脆弱的指令，而是有了一个连贯的框架，让 AI 智能体能够即时发现并使用工具，同时具备恰当的监督与安全。

该协议仍在演进（认证是近期才加入的，而服务器标准化发现等功能也即将到来），但很明显，MCP 或类似的东西将在下一代 AI 应用中扮演关键角色。对开发者来说，现在正是熟悉 MCP 概念的好时机。无论你是在用公司专属知识增强一个聊天机器人，还是在构建能自动化工作流的 AI 智能体，MCP 都能通过处理工具集成的「管道」工作，为你省下时间和麻烦。而且由于它是一个开放标准，背后有不断壮大的社区（以及 Anthropic 等公司）支持，它很可能成为未来 AI 基础设施的一块基石。
