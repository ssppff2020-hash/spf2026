## 编码指令

## Warp 的编码指令：每一件编码任务都从 Warp 开始

1. 每一件编码任务都应该先到 Warp 里写一个提示词。
2. 如果这次编码任务成功了，那太好了！把成功经验分享到 #warped-it
3. 如果过了十分钟，你觉得自己在写提示词上浪费时间……
   1. 请把失败的情况反馈到对应的 #feedback- 频道
   2. 也请分享你的提示词、会话 id 等信息，这样我们能弄清问题出在哪，并有可能围绕它做一个评测
   3. 这也是大家互相交流「如何最好地用 Warp 编码」技巧的机会
4. 接下来，鼓励你换一个 AI 编码工具（比如 Cursor、Claude）试试运气——如果成了，请汇报哪些地方好用、哪些不好用。
5. 最后，就直接手写代码吧……我们得真正把软件发出去，如果手写仍然最快，那就应该手写。

## Warp 的编码指令：为什么

1. 对很多任务来说，用提示词在 Warp 里编码其实更快，应该能提升我们整体的工程产出。
   1. 它能省去你手写代码的时间
   2. 它支持多线程式的并行开发
   3. 当你处理不太熟悉的代码区域时，它尤其有用——随着代码库增长，这样的区域很可能很多——Warp 确实能帮你快速学会代码库的这些新部分
2. 内部试用（dogfooding）自己的产品，是改进它的最好方式。
   1. 这条指令的一个重要理由，就是要去使用我们正在构建的东西并给出反馈。
   2. 我们要求用户这样工作，并把生意押在这上面，那我们自己最好也足够相信这套工作流，愿意亲自使用它
3. 使用竞品能帮我们建立直觉：我们的产品哪些地方可以改进、以及什么是可能的。

## 用 Warp 编码的准则

## 你要对提交评审的代码负责

- 你必须像自己亲手写的一样，完全理解你提交评审的每一行代码
- 智能体模式生成的任何代码，都必须达到我们对亲手写的代码所要求的同一质量水准……
  - 它必须结构良好
  - 它必须有充分的测试
  - 它必须遵循我们的编码规范，包括注释、api、import、测试文件位置等
  - 等等……
- 「这是 AI 写的」绝不能成为 bug 或代码质量差的借口——AI 是工具，不是我们软件团队里能担责的一方
- 用提示词编码时，我们常规的「How We Code」里的所有准则依然适用（小的 PR、功能开关等等）

## 不要只告诉智能体你想要什么结果，要告诉它如何工程化地实现这次改动

- 换句话说，如果你只对智能体说「我想要一个像 X 那样工作的功能」，它很可能产出达不到我们标准的代码。
- 反过来，告诉智能体这个功能该怎么构建
  - 数据模型应该长什么样
  - 我们想要的 api 是什么
  - 代码应该放在哪里
  - 它应该写哪些测试
- 只让智能体围着结果去摸索，最终会浪费大量时间——它产出的代码也许「能跑」，但不可维护、不可测试、不可组合，等等

## 把编码任务拆成更小的组件 / 不要一次性完成大改动

- 你会发现，如果让智能体做小而自足的改动和提交，并频繁确认它没跑偏，用 Warp 编码会更有效
- 一个反模式是试图一次性完成那些需要智能体产出大量代码的复杂改动。简单改动一次性完成没问题，但更复杂的功能就不行。
- 让智能体边做边频繁写测试，是逼它增量推进的好办法。
- 经常查看进行中的改动，确认它的推进方式跟你亲手写时会采取的方式一致。
  1. 目前你可以用 Github 界面或其他 PR 评审工具
  2. 最终 Warp 会更原生地支持这套评审流程
- 让 Warp 在做改动的同时替你提交，并写好提交信息，这样你需要时就能回退

## 确保你理解 Warp 在做什么

- 在 Warp 开始改代码之前，先让它给出解释或计划，这是好习惯
- 反复打磨这个计划，让它给出不同选项和不同实现路径。确保在它开始产出差异之前，你已经掌握了全局
- 反过来，你也可以让 Warp 端到端地做一个大改动，看看它能做到什么程度；但要有心理准备：事后得回头把它拆成能看懂的小块，才能达到我们的质量标准。

## 花时间学习，才能从 Warp 编码中获得最大收益

- 随着你用 Warp 编码越来越多，你会逐渐建立起直觉：该放进哪些上下文、哪类提示最有效，等等
- 请把这些知识分享给团队——用提示词编码是一门全新的技艺，我们每个人对怎么做得好都有不同的直觉。一起学，我们会学得更快。
- 用 Warp 的高级功能来改进你的工作流……
  - 用规则、提示词和 Warp Drive 对象作为持久上下文
  - 用「@」来标记文件
  - 为 UI 改动和调试附上图片
  - 尝试不同的模型
- 在本地搭多份 warp-internal 和 warp-server，这样你就能有效地并行推进多条线

## 上报问题

- 这一点我再怎么强调都不为过——如果有哪里用得不顺，就上报到对应的 #feedback- 频道
- 这可能包括
  - 服务端错误或客户端 bug
  - 智能体绕圈子，白白消耗请求、浪费时间
  - 智能体忘记上下文
  - 缺少能帮你完成任务的某项功能
  - 高延迟、AI 犯蠢、差异应用错位，等等……
- 在处理反馈这一侧，我们对这些问题要做的第一反应，应该是为它们构建评测

- 我们都应该配置的服务器……
  - Sentry

  - <还有什么>

## 为反复出现的约定设置规则

- 花点时间，把你反复要求智能体做的事（比如该跑哪些 linter、我们对 unwrap / expect 的编码约定是什么、import 怎么写、测试放在哪，等等）设成 Warp Drive 规则

## 为重复的工作流设置提示词

- 如果你发现自己在重复某个任务，就值得为它设一个 Warp Drive 提示词。
- 比如，我用提示词来生成提交、创建和编辑 PR 描述、解决合并冲突，等等。
