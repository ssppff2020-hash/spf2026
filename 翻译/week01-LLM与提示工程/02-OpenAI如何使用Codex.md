## 引言

Codex 每天都被 OpenAI 的众多技术团队使用，包括安全、产品工程、前端、API、基础设施和性能工程等团队。这些团队用它来加速一系列工程任务，从理解复杂系统、重构大型代码库，到交付新功能，以及在紧迫的期限下处理事故。

我们整理了与 OpenAI 工程师的访谈以及内部使用数据，汇总出一批使用场景和最佳实践，展示 Codex 如何帮助我们的团队跑得更快、提升工作质量，并在规模化下管理复杂性。

## 使用场景

### 使用场景 1 代码理解

在入职、调试或排查事故时，Codex 帮助我们的团队快速熟悉代码库中不熟悉的部分。

他们常用 Codex 定位某个功能的核心逻辑、梳理服务或模块之间的关系、追踪数据在系统中流转的路径。它还能把架构模式或缺失的文档暴露出来，而这些东西如果靠人工整理，本来要花上可观的精力。

在事故响应过程中，Codex 通过呈现组件之间的交互、追踪故障状态如何在各个系统间传播，帮助工程师快速进入陌生领域。

**来自团队里的真实故事**

> 修 bug 的时候，我用 Ask 模式看看同样的毛病还可能出现在代码库的哪些地方。
> ——性能工程师，检索系统

> 值班时，我把堆栈追踪贴进去，问 Codex 认证流程在哪。它直接跳到正确的文件，让我能快速分诊。
> ——站点可靠性工程师，API 平台

> 我在 Terraform 和 Python 里问「这事我该在哪儿做」这类仓库问题，Codex 回答得比 grep 快得多。
> ——DevOps 工程师，基础设施服务

试用 Codex 做代码理解，可以试试这些示例提示词：

- 这个仓库里的认证逻辑实现在哪里？
- 概述请求如何从这个服务的入口点流经整个服务，直到返回响应。
- 哪些模块与 [insert module name] 交互，失败又是如何处理的？

### 使用场景 2 重构与迁移

Codex 常被用来做跨多个文件或包的改动。比如工程师要更新一个 API、改变某个模式的实现方式，或者迁移到一个新的依赖时，Codex 能轻松地把改动一致地应用下去。

当同一个更新要在几十个文件里重复做，或者这个更新需要感知那些用正则表达式或查找替换难以捕捉的结构和依赖关系时，它尤其有用。

他们还用它做代码清理：拆分过大的模块、用现代模式替换旧模式，或者为更好的可测试性整理代码。

**来自团队里的真实故事**

> Codex 把每一处遗留的 getUserById( ) 都换成了我们新的服务模式，并开了 PR。几分钟就干完了本来要花几个小时的事。
> ——后端工程师，ChatGPT Web

> 为了扫清发布阻塞项，我让 Codex 扫描旧模式的每一处实例，用 Markdown 总结影响，然后带着修复开 PR。
> ——产品工程师，ChatGPT Enterprise

试用 Codex 做重构和迁移，可以试试这些示例提示词：

- 把这个文件按关注点拆成独立模块，并为每个模块生成测试。
- 把所有基于回调的数据库访问都改成 async/await。

### 使用场景 3 性能优化

Codex 被用来发现和解决性能瓶颈。

在做调优或可靠性工作时，工程师会让 Codex 分析慢的或吃内存的代码路径，比如低效的循环、重复的运算、代价高昂的查询，并提出优化方案，往往能在效率和可靠性上带来实打实的提升。

Codex 还被用来维护代码健康：找出那些仍在活跃使用、但有风险或已废弃的模式。我们的团队依靠它来降低长期技术债、主动预防回归。

**来自团队里的真实故事**

> 我用 Codex 扫描反复出现的昂贵数据库调用。它很擅长标出热路径，并起草我之后可以调优的批量查询。
> ——基础设施工程师，API 可靠性

> Codex 很擅长快速发现性能问题——花 5 分钟写提示词，省下 30 分钟的工作。
> ——平台工程师，模型服务

试用 Codex 做性能优化，可以试试这些示例提示词：

- 为提升内存效率优化这个循环，并解释为什么你的版本更快。
- 找出这个请求处理函数里重复的昂贵操作，并指出可以做缓存的地方。
- 为这个函数里的数据库查询提出更快的批处理方式。

### 使用场景 4 提升测试覆盖率

Codex 帮助工程师更快地写测试，尤其是在覆盖率薄弱或完全没有覆盖的地方。

在做 bug 修复或重构时，工程师常让 Codex 提出能覆盖边界情况或可能失败路径的测试。对于新代码，它可以根据函数签名和周边逻辑生成单元测试或集成测试。

Codex 特别善于识别边界条件，比如空输入、最大长度，或者那些不寻常但合法的状态，这些在最初的测试里经常被漏掉。

**来自团队里的真实故事**

> 我把低覆盖率的模块丢给 Codex 过夜，醒来就能拿到可以直接运行的单元测试 PR。
> ——前端工程师，ChatGPT 桌面版

> 切换 mono-repo（单体仓库）分支很痛苦的时候，我让 Codex 写测试并启动 CI，自己继续在分支上干活。
> ——后端工程师，支付与账单

试用 Codex 提升测试覆盖率，可以试试这些示例提示词：

- 为这个函数编写单元测试，覆盖边界情况和失败路径。
- 为这个排序工具生成一个基于性质的测试。
- 扩展这个测试文件，覆盖围绕空输入和非法状态所缺失的场景。

### 使用场景 5 提升开发速度

Codex 通过加速开发周期的两端，也就是开始和收尾，帮助团队跑得更快。

在启动一个新功能时，工程师用它生成样板代码：生成文件夹、模块和 API 桩，快速得到能跑的代码，不用一件件手工接起来。

当项目接近发布时，Codex 通过处理那些更小但必不可少的任务，帮助团队赶上紧迫的期限，比如分诊 bug、填补最后一公里的实现缺口、生成发布脚本、遥测钩子或配置文件。

它还被用来把产品反馈变成起步代码。工程师常把用户需求或规格粘进去，让 Codex 生成一份粗糙的草稿，之后再回来打磨。

**来自团队里的真实故事**

> 我整天在开会，还是合并了 4 个 PR，因为 Codex 在后台干活。
> ——产品工程师，ChatGPT Enterprise

> Codex 帮忙把 3-4 个低优先级修复漂亮地交付了，这些本来会在待办列表里烂掉，这让人特别有掌控感。
> ——全栈工程师，内部工具

试用 Codex 提升开发速度，可以试试这些示例提示词：

- 为 POST /events 搭一个新的 API 路由脚手架，带基本的校验和日志。
- 用这个模板为新的引导流程生成一个追踪成功/失败的遥测钩子 [insert example of your telemetry code]。
- 根据这份规格创建一个桩实现：[insert spec or product feedback]。

### 使用场景 6 保持专注状态

当工程师的日程被切得零碎、充满打断时，Codex 帮助他们保持产出。

它被用来记录未完成的工作、把笔记变成可运行的原型，或者把一个探索性任务单拆出来留待以后回看。这让暂停和恢复工作变得更容易，不会丢掉上下文，尤其是在值班或会议很多的时候。

**来自团队里的真实故事**

> 如果我顺手发现一个要修的地方，我会发一个 Codex 任务，而不是切分支，等有空时再看它的 PR。
> ——后端工程师，ChatGPT API

> 我经常把 Slack 讨论串、Datadog 追踪、issue 等等转发给 Codex，这样我就能专注在优先级高的工作上。
> ——API 工程师，基础设施可观测性

试用 Codex 保持专注状态，可以试试这些示例提示词：

- 生成一个重构这个服务、把它拆成更小模块的计划。
- 把重试逻辑先搭出来并加一个 TODO——稍后我再补上退避逻辑。
- 总结这个文件，好让我明天接着往下做。

### 使用场景 7 探索与构思

Codex 对开放式工作也很有用，比如寻找替代方案或验证设计决策。你可以让它给出解决问题的不同思路、探索不熟悉的模式，或者对假设做压力测试。这有助于呈现取舍、扩展设计选项、让实现选择更清晰。

它也被用来找相关的 bug。给定一个已知问题或一个废弃的方法，Codex 能在代码的其他地方找出相似的模式，让你更容易抓住回归或完成清理工作。

**来自团队里的真实故事**

> Codex 帮我解决冷启动问题——我把规格和文档粘进去，它就生成脚手架代码，或者告诉我漏了什么。
> ——产品工程师，ChatGPT 桌面版

> 修完一个 bug 后，我问 Codex 类似的 bug 可能潜伏在哪里，然后开一批后续任务。
> ——性能工程师，检索系统

试用 Codex 做探索与构思，可以试试这些示例提示词：

- 如果这个系统改成事件驱动、而不是请求/响应，它会怎样工作？
- 找出所有手工拼 SQL 字符串、而不是使用我们查询构造器的模块。
- 用更函数式的风格重写这段代码，避免可变状态和副作用。

## 最佳实践

当 Codex 获得结构、上下文和迭代空间时，它表现最好。下面是 OpenAI 各团队正在培养的一些习惯，用来在日常工作中稳定地获得价值。

### 从 Ask 模式开始

做大改动时，先用 Ask 模式让 Codex 给出一个实现计划，等你切换到 Code 模式时，这份计划就成了后续提示词的输入。这个两步流程让 Codex 有据可依，帮助避免它的输出出现错误。Codex 最适合任务边界清晰、你和队友大约花一小时就能完成、或者需要实现几百行代码的任务。随着模型变强，它能承担的任务规模也会变大。

### 迭代改进 Codex 的开发环境

设置好启动脚本、环境变量和网络访问，能显著降低 Codex 的出错率。跑任务时，留意那些可以通过调整 Codex 环境配置来修正的构建错误。这可能需要迭代几次，但长期看能带来显著的效率提升。

### 像写 GitHub Issue 一样组织你的提示词

当提示词的组织方式和你描述一个 PR 或 issue 里的改动一样时，Codex 的回应更好。也就是说，在相关的地方给出文件路径、组件名、差异（diff）和文档片段。用「按 [module X] 里的做法来实现这个」这类模式来写提示词，效果会更好。

### 把 Codex 任务队列当作轻量级待办清单

把一些支线的想法、半成品工作或顺手要修的东西都发成任务。不必强求一次就生成完整的 PR。Codex 很适合当作一个暂存区，等你重新进入专注状态时再回来处理。

### 用 AGENTS.md 提供持久上下文

维护一个 AGENTS.md 文件，帮助 Codex 在跨提示词的整个仓库中更有效地工作。这类文件通常包含命名约定、业务逻辑、已知的怪癖，或者 Codex 单从代码里推断不出的依赖关系。想了解如何组织你的 AGENTS.md 文件，可以查阅文档。

### 用「Best of N」提升输出质量

Best-of-N 功能让你能针对单个任务同时生成多个回复，快速探索多种方案并挑出最好的一个。对于更复杂的任务，你可以审阅几个迭代版本，把不同回复的部分组合起来，得到更强的结果。

## 展望

Codex 目前仍处于研究预览阶段，但它已经在真实地影响我们构建软件的方式，帮助我们跑得更快、写出更好的代码，并承担那些原本永远不会被排上优先级的工作。

我们对未来的潜力感到兴奋——随着模型变得更好、Codex 更深入地融入我们的工作流，我们期待用它解锁更强大的软件开发方式。我们会继续分享一路上学到的东西。
