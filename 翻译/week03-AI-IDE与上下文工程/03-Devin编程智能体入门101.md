Cognition 团队 2025 年 6 月 · 阅读时长 15 分钟

2025 年了。编程智能体不是什么魔法，但它已经是我们手上最接近魔法的东西了。我们注意到，有些工程师——尤其是 senior 到 staff 级别的——比别人更快地摸到了门道。这里我们分享一些来自客户和我们自身经验的顶级心得。

关于这份指南：

## 与产品无关

我们讨论的这些技巧，能帮你用好任何一种编程智能体。

## 讲究战术

我们给出自己最喜欢的那些可落地建议。

## 技术向

编程智能体对很多人都有价值，但这份指南是站在工程师的角度写的。

开发工具一直在快速演进。十年前，是自动补全和 IntelliSense，能提示方法名、执行程序化的重构。四年前，是 copilot 和 Tab 补全，能帮你写出接下来几行代码。两年前，是生成式聊天机器人，能协助你开发、为你生成整个文件。今天，是自主智能体，能把最初的一段描述一路做成最终的拉取请求，几乎不需要人工介入。过去两年，我们专注于通过构建 Devin 来实现这一愿景。如今，对自主智能体的兴趣达到了新高度，尤其是随着同类产品近期的发布[^1]。这些智能体可以有多种形态，包括 Web 应用、移动应用，以及集成进 Slack、GitHub、Linear、Jira 等流行工具的形态。

一个人类配上 AI 助手，能比任何单独的 AI 做成更多事；而自主智能体端到端处理任务的能力，带来了一个新层次的多任务并行——让每个工程师都变成了工程经理。

适应与这些新 AI 同事高效协作，需要一些时间。有意思的是，我们观察到 senior 到 staff 级别的工程师往往上手最快、最先熟练。最终，这些工具会在各个级别的工程工作中普及。基于我们的经验和客户反馈，我们想分享一些关键洞察和经验教训，帮每个人把这些工具成功融入自己的工作流。

（入门 Getting Started）

## 提示基础

这些基本准则能帮你在 2025 年与编程智能体有效协作。如果别的都记不住，至少记住这些。

### 说清楚你想要怎么做，而不只是做什么

把智能体想象成一个初级编程搭档，它的决策不一定靠谱。简单任务可以直接描述；但更复杂的任务，要一开始就把你偏好的做法讲清楚。提前把整体架构和逻辑交给智能体，不仅能提高成功率，还能减少你评审代码的时间——因为你对预期做法已经心里有数。

#### 示例：

与其说「加点单元测试」，不如指明要测的功能、列出重要的边界情况，并说清楚哪些地方需要 mock（如果有的话）。

### 告诉智能体从哪里开始

想一想：如果这个任务你自己来做，会从哪儿下手？即使不知道具体的文件名或函数名，也要提到相关的仓库、文档和涉及的关键组件。把这些讲清楚，能最大限度减少无效工作和混乱。

#### 示例：

「请给我们的代码加上对 Google 模型的支持。你应该看一下[这里](link)的最新文档，并在 model groups 目录下新建一个实现文件」

### 做防御性提示

想象你把同样的提示词交给一个新来的实习生。哪里容易产生困惑或错误？预判这些点，主动把指令讲清楚，避免歧义。

#### 示例：

「请修好搜索模块的 C++ 绑定，让它通过新的单元测试。注意，你很可能每次改完代码、在测试之前，都需要重新编译绑定。」

### 把 CI、测试、类型和 linter 的访问权限交给它

智能体的魔力，很大一部分来自它能自己修错、能对着报错信息反复迭代。通过类型检查器、linter 和单元测试这类工具提供强有力的反馈回路，能大幅提升它的表现。考虑用带类型的 Python 替代普通 Python，或者用 TypeScript 替代 JavaScript。教你的智能体如何运行常用的检查和测试，确保它有全部所需的依赖包和访问权限。如果智能体可以操作浏览器，就把运行你前端开发环境的步骤清楚地告诉它。

#### 示例：

我们团队从几乎都是无类型的 Python SDK，全面转向了带类型的 SDK（这本身也是一个很适合交给编程智能体的任务）。

### 用好你自己的专业判断

你对代码库越熟悉，上面这些就越容易做到。哪怕是很简单的任务，你能验证逻辑和结果也是加分项。人工监督仍然必不可少——最终，代码的正确性由你负责。即使这些工具越来越精密，所有权和验证仍将是人类工程师的关键职责。

（入门 Getting Started）

## 在工作流中使用智能体

聊智能体的基本功掌握之后，就该把这些 AI 助手带进日常工作了。以下是一些让智能体成为你日常一部分的实用方式：

### 立刻接下新任务

想象一个同事给你发消息：「嘿，能快速做个 X 吗？」或者「我们需要调一下 Y。」与其让它打断你的思路，不如直接给自主智能体发个简短提示，让它去调研或改动。这样你就能继续专注手头的主线任务。有个有意思的副业点子？想快速做个原型、抓点数据，或者复跑一项研究？交给你的智能体，晚点再回来看。

#### 示例：

很多团队在 Slack 上讨论 bug 修复或小功能更新时，直接 @Devin。

### 随时随地写代码

设想你在通勤或出差途中，突然冒出一个紧急 bug，或者你意识到代码里可能留了个错误。别慌！自主智能体通常支持移动端访问，让你能立刻处理这些问题。无论是通过 Slack 的移动 App 还是专门的移动 App，很多智能体都能让你在路上解决问题，哪怕 Wi-Fi 信号很差。

#### 示例：

有了这个可选项之后，我们团队自己在车上和飞机上的效率高了很多。

### 把你的杂活交出去

卡在对旧提交做二分定位，或者要为某个新功能更新文档？把这些重复性任务交给你的智能体。你能省下宝贵的时间，继续专注在更有创造力、更有影响力的工作上。

#### 示例：

在我们团队，工程师发完一个改动后，让智能体更新所有相关文档和面向用户的文案，是很常见的事。

### 不再陷入分析瘫痪

纠结一个重构到底能不能简化代码？在两种架构方案之间选不出来？让你的智能体把两个方案都实现出来。有了具体例子可以对比，决策就变得简单了，而且丢掉一个方案也不会伤谁的感情。

#### 示例：

在文本框要选 Lexical 还是 Slate 时，我们让智能体把两个都实现了。Slate 因为最终效果更好而胜出。

### 搭好预览部署

把你的持续集成/持续交付（CI/CD）流水线设置成：每个新 PR 自动创建预览部署，给你一个立即可用的线上 URL。在评审 AI 智能体完成的前端任务时，这尤其方便。

#### 示例：

Vercel 是一个部署平台，能让预览部署变得超级简单。

（中级 Intermediate）

## 委派更大的工单

当你的拉取请求规模变大、超过几个文件时，一口气处理完就变得困难了。然而，掌握如何委派中等偏大的任务（通常 1–6 小时的工作量），正是自主智能体投资回报率最高的地方。省下的不只是几分钟，而是几小时的产能。小任务也许毫不费力就能跑通，但把智能体的能力拉伸到更大的任务上，回报才最大。

### 自动完成初稿

对于大块头的任务，用自主智能体先做出 PR 的初稿，可以快速启动进度，大幅削减你的工作量。这里成功的关键，是提前把你想要的做法讲清楚。把自己当成指导初级开发者的架构师。清晰、详细的指令，能帮你避免在纠正智能体代码里的根本性误解上浪费时间。

| 领域 | 起草 | 润色 |
|---|---|---|
| 新闻业 | 记者收集初始信息，写出文章初稿 | 编辑审阅草稿、核查事实、打磨，最后定稿发表。 |
| 餐厅 | 流水线厨师准备食材，做出初步的菜品。 | 副主厨加调料、调整菜品口味，然后才送到食客桌上。 |
| 编程 | 自主智能体根据初始计划开工，产出初版解决方案 | 人类开发者审阅草稿 PR，给出反馈，并在合并前做人工打磨 |

🛑 记住，大任务还不是完全无人值守（目前还不是）。更具挑战性的任务，要预期多轮反馈循环，也要预期需要一些人工打磨才能收尾。现实一点的目标是节省大约 80% 的时间，而不是完全自动化；你的专业判断在验证和最终质量把关上依然至关重要。

### 共同编写一份产品需求文档（PRD）

对于复杂或定义模糊的任务，和你的自主智能体一起做一份详细计划，效果可能非常好。一开始不知道所有细节或需求，完全没关系。可以先提示智能体去探索一些发现性问题，比如「我们的认证系统是怎么工作的？」或者「哪些服务可能会受影响？」你也可以让智能体找出具体的相关代码位置，供你早早确认。

某些智能体，比如 Devin 和 Claude Code，提供专门的规划模式，重点是阅读和探索已有代码，而不是立刻改动它。如果你希望在委派任务前做更深的准备，deepwiki.com 和 Devin Search 这类专门的代码库搜索工具，能快速给你关于代码库的洞察，帮你简化流程。

### 设置检查点

对于多阶段任务，尤其是涉及多个代码库的，要沿途设立清晰的检查点：

计划 → 实现一个分块 → 测试 → 修复 → 检查点评审 → 下一个分块

要明确要求智能体在每个重要阶段后暂停，尤其是跨多层（例如数据库、后端、前端）构建的复杂功能。利用这些检查点确认实现符合你的预期、澄清疑问（例如「解释一下认证流程，并确认它的安全性」），并及时纠偏，避免问题连锁爆发。

#### 示例：

「我想让你实现这个功能，它会横跨我们的数据库、后端和多个前端界面。请先规划数据库 schema 需要的改动，做完告诉我，我来执行迁移。」->「现在请实现后端的改动，并加上测试，确保 XYZ 能正常工作。做完告诉我」->「现在在 Web 和移动端两个界面里实现改动，调用新的后端接口」

### 教它验证自己的工作

给反馈的时候，别只是指出问题（「这个函数不工作」）。把你的测试流程讲清楚，让智能体将来能独立验证任务。对于你会反复用到的测试模式，把它们写进智能体的长期知识库（见「加入智能体的知识库」）。

#### 示例：

在 Devin 中，我们会主动提示用户把关键的测试流程保存到智能体的长期记忆中，从而简化未来的交互。

### 提高 AI 热区的测试覆盖率

目前，智能体还无法完全地、交互式地彻底测试所有场景。在 AI 频繁改动的区域提升测试覆盖率，能让你对智能体的产出更有信心。扎实的测试意味着，看起来正确的代码可以放心合并，不必担心。

#### 示例：

我们团队在把实现从 Python 翻译到 C 之前，先加强了代码库中某个关键部分的单元测试。

（高级 Advanced）

## 自动化工作流

智能体响应传入事件的速度比人快得多，而且比起人类同事，它们更愿意做无聊、重复的工作。

### 为最重复的工作创建快捷方式

工程团队经常遇到重复、例行的事务。这些正是交给智能体自动化的完美候选。常见例子包括：

- 移除功能开关
- 升级依赖
- 在新功能 PR 上修复和补充测试

要高效地搭好这套东西，通常由有经验的工程师创建一个健壮、可复用的提示词模板[^2]。

#### 示例：

我们有位客户在新功能开发出来时，会自动触发三个专门写单元测试的智能体。

### 智能代码评审与规则落地

虽然已有专门做快速代码评审的工具[^3]，但自主智能体也可以是一个有意思的选择，能给出更准确的洞察——特别是当它们已经索引了你仓库的功能之后。

#### 示例：

在 Cognition，我们喜欢维护一份「工程师最常犯的错误」清单，并把它提交到代码库里。然后，我们不写传统的 lint 规则来抓这些问题（这往往做不到），而是让一个智能体在每个新 PR 上运行，检查这些错误。

### 接入事故与告警

你也可以把自主智能体设置成在特定事件发生时自动触发。例如，Devin 提供了方便调用的 API，其他智能体也可以通过 CLI 命令接入自定义工作流。这些方案与模型上下文协议（MCP）服务器配合时效果尤其好，可以接收第三方的错误日志。

⚠️ 在生产服务里分诊问题时，AI 的调试能力并不算好。与其让 AI 端到端地修 bug，不如让 AI 只把最可疑的错误、改动等标出来，这样往往更实际。

（高级 Advanced）

## 定制与性能提升

### 环境搭建

再没有比不完整或版本不匹配的环境更能拖慢智能体的了。为了让它顺畅运行，要让智能体的环境和你团队的环境完全对齐，包括语言版本、依赖包和自动化检查。例如，智能体环境里应该装好 pre-commit，环境配置（密钥、语言版本、虚拟环境、浏览器登录态）应该用 .envrc 或自定义的 .bashrc 配置自动加载。

#### 示例：

我们把智能体的浏览器配上预先认证好的登录态，省去了手动认证的麻烦，测试起来方便多了。

### 构建自定义 CLI 工具和 MCP

MCP 已经广泛可用，设置起来很快，也很适合拿来试验如何把智能体连接到外部工具[^4]。但很多人忽略了为智能体写一些简单的 CLI 脚本。举个简单的例子，你可以给智能体一个脚本，输入工单 ID 就能拉取该 Linear 工单的信息。你也可以给智能体一个工具，用来可靠地完成工作流里常见的环节，比如一个重启本地开发环境的脚本。

#### 示例：

我们有一位客户，做了一个只展示测试套件中第一个失败用例的 CLI 工具，效果非常好。这个 CLI 会引导智能体只专注那一个测试，并给出详细的错误信息，从而让智能体在长任务上的成功率和完成速度都更高。

### 加入智能体的知识库

如果你的智能体总犯某些常见错误，那就是把反馈固化进智能体知识库的好时机。在 Devin 里有一个专门的知识管理系统。很多产品提供 .rules 文件、.md 文件，供智能体永久吸收。不要只给它关于你所使用框架的准则，也要告诉它你项目的整体架构。告诉它不同类型的任务通常用什么测试、如何运行重要命令，以及你推荐使用哪些工具。

#### 示例：

我们把「新增一个服务路由时应该遵循的具体流程」写进智能体的知识里。这些信息包括前端和后端所有需要添加样板代码的位置。结果，这类任务现在可以轻松交给我们的 AI 了。

（实践考量 Practical Considerations）

## 自主智能体的局限

### 调试能力有限

Bug 报告看起来可能很简单。但很多 bug 往往不仅需要访问数据库和日志，还需要超出当下大多数 AI 智能体的调试水平。如果用 AI 辅助调试，我们建议让它给出一份可能根因的清单，而不是让它自己去调试和修复一切。然后由人根据自己的经验判断哪一个是真正的根因。但根因一旦明确，智能体在实现修复方案上仍然能帮上不少忙。

### 细粒度视觉推理能力差

一般来说，当今的模型在匹配设计稿截图或 Figma 原型所需的细节层面上，视觉推理能力并不好。它们最可靠的是能用代码描述的视觉内容（例如，把 Figma 里的代码交给它）。如果你想让输出匹配你的视觉风格，应该使用带可复用组件的好设计系统。

### 知识截止

每当你要用一个新库，都应该明确把它指向最新的文档。否则，由于预训练基座模型的知识截止，大多数智能体会沿用这些库的旧模式。好的智能体在你把文档指给它之后能克服这个问题，但你必须留意这一点（记住，智能体甚至不知道这些库有新版）。

（实践考量 Practical Considerations）

## 管理时间与减少损失

并非每次使用智能体都会成功。2025 年，这些智能体的产出结果确实存在不小的差异。这份工作的一部分，就是学会怎么用智能体，才能最大化碰上好结果的概率，同时把浪费的时间和 token 降到最低。

### 愿意更早止损

新手常犯的一个错误是：即使智能体的工作已经明显跑偏，也要硬把它做成功。如果你发现自己心里在想「它不理我的指令」或者「这东西在绕圈子」，那你完全可以中止这段对话，或者自己接手。继续发更多消息，更可能是说明你的任务本身复杂度超过了智能体的能力，而不是某个简单错误可以纠正。

### 让实验多样化

如果你是新手，我们建议一开始就把赌注分散开。尝试各种不同的提示词和想法。对那些智能体天然表现良好的任务类型加大投入，对表现不好的果断止损。不必强求智能体每次都成功。

### 没有进展时就重新开始

在智能体身上，「重开一局」是正确答案的次数，比在人身上多得多。如果你给智能体派了任务，而它在处理反馈、纠正方向上很吃力，那么换一个新智能体、把所有指令一次给全，重新开始，往往能更快成功。智能体修复乱掉的环境的能力，远不如它从头生成干净代码的能力。

（实践考量 Practical Considerations）

## 安全与权限

### 为你的智能体创建账号

一次性邮箱有助于安全地测试各类站点。如果智能体需要访问云资源，为它创建自定义的 IAM 角色。

### 给它一个开发 / 预发布环境

理想情况下，智能体使用与你团队工程师相同的测试配置。我们建议完全不要给它生产服务的访问权限。使用远程智能体时，你可以在智能体的远程机器上运行完全隔离的测试环境。

### 只读 API 密钥

在可能的情况下，给它只读权限。我们发现，让人类手动运行任何与外部服务交互的脚本，仍然是有帮助的。

（实践考量 Practical Considerations）

## 前方有重大变化

我们坚信，软件工程师不会消失。即使编程智能体变得更聪明、更强，深厚的技术专长和对代码库的熟知依然极其宝贵。真正对自己项目、系统和代码拥有所有权，如今比以往任何时候都更重要。今天在我们团队，工程师要同时照看多个系统，并保持深入的理解和审慎的判断。当自动化放大你的影响力时，「并行处理多个任务」的能力将不只是可行，而是必需。我们很高兴分享在让自身组织为这一转变做准备时收获的洞见，让你和你的团队也能在软件开发的这个演进世界中蓬勃发展。
