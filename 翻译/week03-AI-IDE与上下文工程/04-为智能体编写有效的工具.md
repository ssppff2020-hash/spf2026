智能体的效能，取决于我们给它的工具。我们分享如何编写高质量的工具与评测，以及如何用 Claude 来为它自己优化工具，从而提升表现。

模型上下文协议（MCP）能让 LLM 智能体拥有数百个工具，去解决真实世界的任务。但我们要怎么让这些工具发挥最大效能？

本文中，我们介绍在一系列智能体化的 AI 系统中提升表现的最有效技巧[^1]。

首先，我们会讲如何：

- 构建并测试你的工具原型
- 用智能体对你的工具创建并运行全面的评测
- 与 Claude Code 这样的智能体协作，自动提升你工具的表现

最后，我们总结在此过程中发现的高质量工具编写的关键原则：

- 选择要实现哪些工具（以及不实现哪些）
- 用命名空间（namespacing）划分工具，明确功能边界
- 从工具向智能体返回有意义的上下文
- 为 token 效率优化工具响应
- 对工具描述和规格做提示工程

建立评测体系，让你能系统地衡量工具的表现。你可以用 Claude Code 针对这个评测自动优化你的工具。

## 什么是工具？

在计算机领域，确定性系统在给定相同输入时，每次都会产生相同的输出；而非确定性系统——比如智能体——即使起点相同，也可能产生不同的响应。

传统上我们写软件，是在确定性系统之间建立一份契约。例如，像 getWeather("NYC") 这样的函数调用，每次调用都会以完全相同的方式获取纽约市的天气。

工具是一种新型软件，它体现的是确定性系统与非确定性智能体之间的契约。当用户问「我今天该带伞吗？」，智能体可能会调用天气工具、凭常识回答，甚至先追问一句地点。偶尔，智能体也可能产生幻觉，甚至根本没搞清楚该怎么用某个工具。

这意味着我们为智能体写软件时，需要从根本上重新思考做法：不能再像给其他开发者或系统写函数和 API 那样去写工具和 MCP 服务器，而要**为智能体**设计它们。

我们的目标，是扩大智能体能够有效发挥作用的「面积」——让它能借助工具，在各种各样的任务上采取各种成功的策略。幸运的是，以我们的经验，对智能体来说最「顺手」的工具，往往也对人类出奇地直观。

## 如何编写工具

本节讲如何与智能体协作，既写出工具，也改进你交给它的工具。先快速搭起工具原型，在本地测试。接着跑一轮全面的评测，衡量后续的改动。与智能体一起工作，你可以反复进行「评测—改进」的循环，直到你的智能体在真实任务上表现强劲。

### 构建原型

如果不亲手试一试，很难预判哪些工具智能体会觉得顺手、哪些不会。先快速搭起工具原型。如果你用 Claude Code 来写工具（也可能一次就成），给 Claude 提供工具所依赖的任何软件库、API 或 SDK（可能包括 MCP SDK）的文档会很有帮助。LLM 友好的文档通常能在官方文档站点的扁平 llms.txt 文件中找到（这里有一份是我们 API 的）。

把工具包在本地 MCP 服务器或桌面扩展（DXT）里，你就能在 Claude Code 或 Claude Desktop 应用中连接并测试它们。

要把本地 MCP 服务器连接到 Claude Code，请运行 claude mcp add <name> <command> [args...] 。

要把本地 MCP 服务器或 DXT 连接到 Claude Desktop 应用，请分别前往 Settings > Developer 或 Settings > Extensions 。

工具也可以直接传入 Anthropic API 调用，用于程序化测试。

自己动手测试这些工具，找出任何粗糙的地方。从你的用户那里收集反馈，建立起对预期用例和预期提示词的直觉。

### 跑一轮评测

接下来，你需要通过跑一轮评测来衡量 Claude 使用你工具的效果。先基于真实世界的用法，生成大量评测任务。我们建议与智能体协作，帮它分析你的结果，并确定如何改进你的工具。在我们的工具评测 cookbook 里可以看到这个流程的端到端演示。

> 图：我们内部 Slack 工具的留出测试集表现

生成评测任务

有了早期原型，Claude Code 可以快速探索你的工具，生成几十组提示词—响应对。这些提示词应当受真实用法启发，并基于真实的数据源和服务（例如内部知识库和微服务）。我们建议避开过于简单或表面的「沙箱」环境——那样的环境无法以足够的复杂度对你的工具施压。好的评测任务可能需要多次工具调用——可能是几十次。

下面是一些强任务的例子：

- 下周和 Jane 安排一场会议，讨论我们最新的 Acme Corp 项目。附上上次项目规划会的笔记，并预订一间会议室。
- 客户 ID 9182 反馈，他一次购买尝试被扣了三次款。找出所有相关日志条目，并判断是否还有其他客户受到同一问题影响。
- 客户 Sarah Chen 刚提交了取消请求。准备一份挽留方案。要确定：(1) 他们为什么离开，(2) 哪种挽留方案最有吸引力，(3) 在报价之前我们应该知道哪些风险因素。

下面是一些较弱的任务：

- 下周和 jane@acme.corp 安排一场会议。
- 在支付日志中搜索 purchase_complete 和 customer_id=9182 。
- 找到客户 ID 45892 提交的取消请求。

每个评测提示词都应配一个可验证的响应或结果。你的验证器可以简单到把标准答案与采样响应做精确字符串比对，也可以复杂到请 Claude 来评判响应。避免过于严格的验证器——它们会因为格式、标点或合理的替代表述这类无关紧要的差异，把正确答案判为错误。

对于每个提示词—响应对，你还可以选择性地指定你期望智能体在解决任务时调用的工具，从而在评测中衡量智能体是否成功领会了每个工具的用途。不过，由于正确解决任务可能存在多条有效路径，要尽量避免过度指定或过拟合到某种策略。

运行评测

我们建议用直接的 LLM API 调用，以程序化的方式运行评测。使用简单的智能体循环（用 while 循环包裹交替进行的 LLM API 调用和工具调用）：每个评测任务一个循环。每个评测智能体应获得单个任务提示词和你的工具。

在评测智能体的系统提示词中，我们建议指示智能体不只输出结构化的响应块（用于验证），还要输出推理和反馈块。在工具调用和响应块之前，指示智能体输出这些内容，可以通过触发思维链（CoT）行为，提升 LLM 的有效智能水平。

如果你用 Claude 运行评测，可以打开交错思考（interleaved thinking）来「开箱即用」地获得类似功能。这能帮你探查智能体为什么调用或不调用某些工具，并指出工具描述和规格中需要改进的具体之处。

除了顶层准确率，我们还建议收集其他指标，比如单个工具调用和任务的运行总时长、工具调用总次数、token 总消耗量以及工具错误。追踪工具调用有助于发现智能体常走的通用工作流，也能为工具合并整合提供一些机会。

分析结果

智能体是你发现问题和获取反馈的好帮手：从自相矛盾的工具描述，到低效的工具实现、令人困惑的工具 schema，都能给你反馈。但请记住，智能体在反馈和响应中**遗漏**的内容，往往比**包含**的内容更重要。LLM 并不总是言为心声。

观察你的智能体在哪里卡住或困惑。通读评测智能体的推理和反馈（也就是 CoT），找出粗糙之处。查看原始对话记录（transcript，包括工具调用和工具响应），捕捉任何智能体 CoT 中没有明确描述的行为。要读出字里行间的意思；记住，你的评测智能体并不一定知道正确答案和正确策略。

分析你的工具调用指标。大量冗余的工具调用，可能说明分页或 token 上限参数需要调一调；大量因参数无效导致的工具错误，可能说明工具需要更清晰的描述或更好的示例。我们在发布 Claude 的网页搜索工具时发现，Claude 会无谓地在工具的 query 参数后面加上 2025，使搜索结果产生偏置、降低表现（我们通过改进工具描述把 Claude 引回了正确方向）。

### 与智能体协作

你甚至可以让智能体帮你分析结果、改进工具。只要把评测智能体的对话记录拼接起来，粘贴进 Claude Code 即可。Claude 擅长分析对话记录，并一次性重构大量工具——例如，在做出新改动时，确保工具的实现和描述保持自洽。

事实上，本文中大部分建议，都来自我们用 Claude Code 反复优化内部工具实现的过程。我们的评测建立在自己的内部工作区之上，复刻了内部工作流的复杂度，包括真实的项目、文档和消息。

我们依靠留出测试集，来确保没有对「训练」用的评测过拟合。这些测试集表明，即使超出了我们用「专家级」工具实现所达到的水平，我们还能挖掘出额外的性能提升——无论那些工具是由我们的研究人员手写的，还是由 Claude 自己生成的。

下一节，我们会分享从这个过程中学到的一些东西。

## 编写有效工具的原则

本节我们把经验提炼成几条指导原则，用于编写有效的工具。

### 为智能体选择合适的工具

工具更多，并不总是带来更好的结果。我们观察到的一个常见错误是：工具只是把已有的软件功能或 API 端点包了一层——不管这些工具是否适合智能体。这是因为智能体相对于传统软件有不同的「可供性」（affordance）——也就是说，它们感知自己能拿这些工具做哪些潜在动作的方式不同。

LLM 智能体的「上下文」是有限的（也就是说，它们一次能处理的信息量有上限），而计算机内存既便宜又充裕。想想在通讯录里找一个联系人的任务。传统软件程序可以高效地存储和处理联系人列表，一次检查一个，检查完再往下走。

然而，如果 LLM 智能体用的工具返回**全部**联系人，然后它不得不逐 token 地读一遍，那就是在把有限的上下文空间浪费在无关信息上（想象你从上到下逐页翻通讯录找一个人——也就是暴力搜索）。更好、也更自然的做法（对智能体和人类都一样）是先翻到相关的那一页（也许按字母顺序找到它）。

我们建议针对少数几个高影响力的具体工作流，先构建几个经过深思熟虑的工具——它们要与你的评测任务相匹配——再在此基础上扩展。在通讯录这个例子里，你可以选择实现 search_contacts 或 message_contact 工具，而不是 list_contacts 工具。

工具可以整合功能，在底层处理可能是多个离散操作（或 API 调用）。例如，工具可以在响应里补充相关元数据，或者在单次工具调用里处理经常被串起来的、多步骤的任务。

下面是一些例子：

- 与其实现 list_users 、list_events 和 create_event 工具，不如考虑实现一个 schedule_event 工具，它负责查找空闲时间并安排事件。
- 与其实现 read_logs 工具，不如考虑实现一个 search_logs 工具，它只返回相关的日志行和少量周边上下文。
- 与其实现 get_customer_by_id 、list_transactions 和 list_notes 工具，不如实现一个 get_customer_context 工具，一次性汇总某个客户近期且相关的全部信息。

确保你构建的每个工具都有清晰、独特的用途。工具应当让智能体能够像人类在拥有同样底层资源时会做的那样，把任务拆解并解决；同时减少那些本来会被中间输出消耗掉的上下文。

工具太多或功能重叠，也会分散智能体追求高效策略的注意力。对要构建（或不构建）哪些工具做谨慎、有选择的规划，回报可能很可观。

### 为工具分命名空间

你的 AI 智能体可能会获得数十个 MCP 服务器和数百个不同的工具——包括其他开发者提供的。当工具功能重叠或用途模糊时，智能体可能搞不清该用哪个。

分命名空间（把相关工具归到共同的前缀下）有助于在众多工具之间划清边界；MCP 客户端有时默认就会这么做。例如，按服务为工具分命名空间（如 asana_search 、jira_search），或按资源分（如 asana_projects_search 、asana_users_search），能帮智能体在恰当的时候选到恰当的工具。

我们发现，在前缀式命名空间和后缀式命名空间之间做选择，对我们的工具调用评测有不可忽视的影响。影响因 LLM 而异，我们鼓励你根据自己的评测来选择命名方案。

智能体可能会调错工具、用错误的参数调对工具、调用的工具太少，或者错误地处理工具响应。通过有选择地实现那些名称能反映任务自然划分的工具，你可以同时减少载入智能体上下文的工具数量和工具描述数量，并把智能体化的计算从智能体的上下文卸载到工具调用本身。这会降低智能体犯错的整体风险。

### 从工具返回有意义的上下文

同样地，工具实现应当注意只向智能体返回高信号的信息。它们应当把上下文的关联性置于灵活性之上，并避开底层的技术标识符（例如 uuid 、256px_image_url 、mime_type）。像 name 、image_url 和 file_type 这样的字段，更有可能直接影响智能体的下游动作和响应。

智能体处理自然语言的名称、术语或标识符，通常比处理晦涩的标识符成功得多。我们发现，仅仅把任意的字母数字 UUID 解析成更有语义、更易解读的语言（甚至只是一个从 0 开始编号的 ID 方案），就能通过减少幻觉，显著提升 Claude 在检索任务中的精度。

在某些情况下，智能体可能需要同时与自然语言和技术标识符输出打交道的灵活性，哪怕只是为了触发下游的工具调用（例如 search_user(name=’jane’) → send_message(id=12345) ）。你可以在工具里暴露一个简单的 response_format 枚举参数来同时支持两者，让智能体自己控制工具返回「简洁」还是「详细」的响应（见下图）。

你可以加入更多格式来获得更大的灵活性，类似 GraphQL 那样，让你精确选择想要收到哪些信息。下面是一个控制工具响应详细程度的 ResponseFormat 枚举示例：

```

    DETAILED = "detailed",
    CONCISE = "concise"
```

### 为 token 效率优化工具响应

优化上下文的质量很重要。但优化返回给智能体的上下文数量——也就是工具响应——同样重要。

我们建议对任何可能消耗大量上下文的工具响应，采用分页、范围选择、过滤和/或截断的某种组合，并设置合理的默认参数值。对于 Claude Code，我们默认把工具响应限制在 25,000 token。我们预计智能体的有效上下文长度会随时间增长，但对上下文高效的工具的需求会一直存在。

如果你选择截断响应，务必用有用的指令引导智能体。你可以直接鼓励智能体采用更省 token 的策略，比如在知识检索任务中做多次小而精准的搜索，而不是一次宽泛的大搜索。同样，如果某次工具调用报错（例如在输入校验期间），你可以对错误响应做提示工程，清楚地传达具体、可操作的改进方向，而不是给出晦涩的错误码或堆栈回溯。

### 对工具描述做提示工程

现在我们来到改进工具最有效的方法之一：对你的工具描述和规格做提示工程。因为它们会被载入智能体的上下文，它们能共同引导智能体形成有效的工具调用行为。

写工具描述和规格时，想想你会怎么向团队里新来的人介绍这个工具。考虑你可能默认带入的上下文——特殊的查询格式、生僻术语的定义、底层资源之间的关系——并把它们明说出来。通过清楚地描述（并用严格的数据模型强制）预期的输入和输出，来避免歧义。尤其是输入参数应当命名得毫无歧义：与其用名为 user 的参数，不如用名为 user_id 的参数。

有了评测，你就能更有把握地衡量提示工程带来的影响。哪怕对工具描述做很小的改进，也能带来显著的提升。在我们对工具描述做了精确的改进之后，Claude Sonnet 3.5 在 SWE-bench Verified 评测上达到了当时的最优表现，错误率大幅下降，任务完成度提升。

你可以在我们的开发者指南中找到工具定义的其他最佳实践。如果你在为 Claude 构建工具，我们还建议阅读工具是如何被动态加载进 Claude 的系统提示词的。最后，如果你在为 MCP 服务器写工具，工具注解（tool annotations）有助于说明哪些工具需要开放世界的访问权限，或会做出破坏性改动。

## 展望

要为智能体构建有效的工具，我们需要把软件开发实践从可预测的、确定性的模式，重新转向非确定性的模式。

通过本文描述的这套迭代的、评测驱动的流程，我们识别出了一些让工具成功的稳定规律：有效的工具被有意地、清晰地定义；审慎地使用智能体的上下文；能在多样的工作流中组合使用；并让智能体直观地解决真实世界的任务。

未来，我们预计智能体与世界交互的具体机制会不断演进——从 MCP 协议的更新，到底层 LLM 本身的升级。有了这套系统的、评测驱动的方法来改进面向智能体的工具，我们就能确保：当智能体变得更强时，它们使用的工具也会随之演进。
