## 规格已死，规格万岁！

### 原型是新的规格，而规格是新的……源代码？

Ravi Mehta 与 Danny Martinez

2025 年 7 月 31 日

在我的职业生涯里，规格越写越短。我刚进 Microsoft 时，衡量一个 PM（产品经理）价值的标准，是他写的规格有多重。多年之后，在 Tripadvisor，我们把那位带着一张餐巾纸上潦草写就的规格走进产品评审会的 PM 传成了传奇。

产品团队常常把规格当成文书工作——发货这件「正经事」之前不得不忍受的麻烦。工程师因优雅的代码受到赞美，设计师因漂亮的 UX 受到赞美，PM 因交付了影响力而获得称赞。可规格呢？它通常被草草带过、随手一扔、转头就忘。

这一直是个错误。在我的《产品能力工具包》里，「功能规格」排在十二项能力之首，这是有原因的。它和产品交付、产品质量一起，支撑起产品执行。

无懈可击的执行是优秀产品管理的根基，而一份出色的规格就是起跑线。

今天，我们构建产品的方式正在转变。工程师变得更快了——快得多。AI 能在几分钟内把粗糙的想法变成能跑的代码。瓶颈不再是构建本身，而是知道该构建什么，并让团队围绕这些需求达成一致。

一夜之间，不起眼的规格不再是转瞬即逝的文书。它是产品管理的根基——它正在变成源代码本身。

## 为什么 PM 突然成了瓶颈

在最近那场演讲《用 AI 更快地构建》（Building Faster with AI）中，Andrew Ng 指出了一个前所未有的趋势：

> 「我人生中第一次见到有管理者向我提议，让 PM 的数量是工程师的两倍。我至今不知道这个提议是不是好主意，但我认为它是一个信号，说明世界正走向何方。」——Andrew Ng

这印证了我们在上一篇文章中的预测：当工程师借助 AI 把交付速度提升数倍时，公司需要的是更多 PM 去支撑这些高产的工程师，而不是更少。

随着产品交付提速，产品管理的其他每一环都承受着巨大压力——理解客户需求、打磨正确的功能、验证影响力。

而所有这些压力，最终都汇聚到一件产物上——规格。

## 规格——新的源代码

在传统软件开发中，程序员编写人类可读的「源代码」，它会被编译成高度优化、机器可读的「目标代码」（object code）。目标代码（也叫二进制文件）是副产物，用源代码就能重新生成。源代码字面意义上就是事实来源。

来自 OpenAI 的 Sean Grove 提出了一个颇具争议的论点。在最近那场演讲《新的代码》（The New Code）中，他主张一份写得很好的提示词（也就是规格）就是新的源代码。

从这个角度看，我们把 AI 开发做反了。我们精心撰写提示词，把意图传达给模型。AI 生成代码。然后我们留下代码，把提示词扔掉。

> 「这感觉就像你把源代码碎掉，然后非常仔细地对二进制文件做版本控制。」Grove 这样评论。

想想这件事。在传统编程里，源代码是神圣的。源码里有注释、结构、文档——理解系统、修改系统所需的一切。二进制文件只是一个下游产物。

但在 AI 时代，我们把这个关系翻转了。我们把生成的代码当成值得留下的产物，而把规格——也就是提示词——当成用完即弃的东西。

Grove 认为这完全搞反了。代码，哪怕是优雅的代码，也只是他所说的、从规格投影出来的「有损投影」（lossy projection）。就像反编译二进制文件拿不回原本的注释和变量名一样，读代码也读不出它背后的完整意图。

而规格包含一切。一份足够健壮的规格能生成「优秀的 TypeScript、优秀的 Rust、服务端、客户端、文档、教程、博客文章，甚至播客」。

> 「一份足够健壮的规格能生成优秀的 TypeScript、优秀的 Rust、服务端、客户端、文档、教程、博客文章，甚至播客。」——Sean Grove，OpenAI

更重要的是，规格能做到代码做不到的事：让人类和机器就共同目标达成一致。Grove 说得很直白：「一份写下来的规格能有效地让人类对齐，它是你用来沟通、讨论、辩论、援引并同步的产物。」

他预测：「在不远的将来，沟通最有效的人就是最有价值的程序员。而且说真的，只要你能有效沟通，你就能编程。」

新的稀缺技能不是编程，而是写出能完整承载意图与价值的规格。

对产品经理来说，这听起来应该很熟悉。这正是我们一直在做的事——只不过现在机器也在听。

## 等等，原型不是已经把规格杀死了吗？

直到不久之前，产品生命周期都必须以规格（或产品需求文档 PRD、概念文档、餐巾纸）开头，由它启动最初的线框图（wireframes）、设计、原型和 MVP（最小可行产品）开发。

传统做法感觉像一种不得不忍受的恶。工程师先做出基础 MVP，把某个东西——随便什么东西——交到客户手里。「如果你对产品的第一版不感到尴尬，那说明你发布得太晚了」成了信条。

我们构建产品的整套方法最近发生了重大转变；在这个新世界里，规格往往是产出，而不是输入。

今天，你不需要交付一行代码，就能把原型交到客户手里。v0、Lovable、Replit 这类工具让你在几小时内——而不是几周内——搭建出能跑的原型。不需要工程投入。

这不仅仅是更快——这是根本性的不同。拿着一个「vibe coding 出来的」原型，你可以在写下功能规格的第一行之前，就收集到真实的客户反馈。你可以验证假设、迭代流程、打磨交互。

旧的工作流是这样的：模糊的想法 → 线框图 → 设计 → 工程师搭建的 MVP → 客户反馈 → 痛苦的规格修订 → 线框图 → 设计 → 重做 → 祈祷。

新的工作流：模糊的想法 → 快速原型 → 客户反馈 → 清晰无比的规格 → AI 辅助实现。

原型没有杀死规格。它们正在让规格变得更好。

## 规格驱动开发的实战

我们来看一个亲手操作的例子，看看这一切如何落地。Danny Martinez 是 decimals 的创始人，这是一个（处于隐身开发阶段 stealth 的）平台，让创作者经济中的专家能把自己人脉里的人才安置到岗位上。

你是 AI 优先的 PM，正在寻找新机会吗？留下你的信息，我们碰到有意思的机会时会通知你。

你是想招聘 AI 优先 PM 的公司吗？申请加入我们的人才网络，我们会分享一份精选的候选人名单。

Danny 将带我们走一遍他们的规格驱动开发流程——这个流程带来了两个影响：

- 对于较大的功能，与工程团队的沟通大幅改善；
- 让此前毫无编程经验的 Danny，在小功能上也能从详细规格一路做到上线功能。

交给 Danny……

以下是我最近做的一个例子。背景是：我们在构建一个产品，让专家型影响者能把自己人脉中的候选人安置到岗位上。上线一个新的落地页（landing page）之后，我们需要让专家们有一个快速获取自己页面链接的办法。

> 我们需要在页眉加一个按钮，指向公司申请页面。我目前在忙邮件这块。如果这个你能接手的话，是可以用 vibe coding 做的。

这来自我的联合创始人，说的只是一个需要上线的简单按钮。足够简单，而且恰恰是如今非技术背景的人自己就能上线的那类事情。

下面是这套配置，以及它如何在几分钟内上线：

- 项目管理工具：Linear
- IDE（集成开发环境）：VS Code
- 扩展：GitHub Copilot Pro
- 模型：Claude Sonnet 4
- MCP 服务器：Linear MCP server，让 Linear 工单（ticket）可以通过 Copilot 访问

我们来看看这个流程中的步骤（可以跟着上面的 Loom 视频一起做）：

1. 从我联合创始人发在 Slack 的消息生成一个 Linear 工单（00:14）
2. 在上述工单里明确我想让新文案写成什么（00:25）
3. 打开 Copilot，让 Claude 打开这个 Linear 工单（01:18）
4. 让 Claude 审阅这个工单，并对照代码库分析它（01:52）
5. 让 Claude 创建一个分支并实现这些改动（02:30）
6. 测试改动，确认它们按预期工作。（02:52）
7. 在 GitHub 上开一个拉取请求（PR），把这些改动合入代码库（03:55）
8. 等工程师评审/批准这个 PR

把镜头拉远，这套配置真正的威力就清晰起来了。没错，这是个微不足道的例子，但道理不变：一个非技术背景的人现在可以在 Linear 工单、代码库和工程师之间穿梭，靠的只是通过 GitHub Copilot 给 Claude 的几个提示词。

再说一次，这一切的关键不是代码本身，而是规格。

现在，有必要给上面的说法加个前提，说明它要跑得好需要什么：

- **要具体**：用模糊的规格，只会得到一团乱的代码库。让 Claude 拿工单的初稿、审阅代码库、帮忙把它写得更具体，是这个流程中不可或缺的一环。在我们的例子里，我们还有一份写好规格的指南。
- **要有选择性**：上述做法用在较简单的任务上最理想。工单越复杂，就越需要懂行的人参与进来（这些情况下，「自助」最后往往一点都不自助）。
- **要有人把关**：这个做法之所以效果好，只是因为有真正懂行的工程师在评审改动，确保在简单与功能之间保持平衡。

但要说清楚：规则已经变了。规格是所有参与构建产品的人的事实来源，包括 LLM。

配置得当的话，非技术背景的人期待自己能给代码库做贡献，是完全现实的。只要有足够的时间和耐心，你可以开始理解代码库，自己实现改动，而不是每次都靠 Claude 来救场。

有一天，你甚至可能期待一个 AI 智能体在你抿咖啡的时候就把你的工单交付了。

如果你是一名 PM，在担心 AI 会对你的工作做什么，关键是意识到这份工作本身正在改变。但其他人也一样。好在，成为一名优秀 PM 所需的核心技能，在这个新世界里反而更值钱了。

正如我们在上一篇文章中预测的，以这种方式运作的公司，需要的是更多 PM，而不是更少。而且这个预测落实得相当不错：

## 规格万岁！

创造了「赛博空间」（cyberspace）一词的科幻作家 William Gibson 曾说：

> 未来已经到来——只是分布得还很不均匀。

当我思考 AI 能做什么、不能做什么时，就会想起这句话。今天，AI 的进步极不均衡。有些事情——生成代码、文本、图像——实现了量子跃迁式的发展，它们以「AI 速度」运转。另一些事情——跟客户交谈、发现他们的需求、说服他们购买——仍然以「人类速度」前进。

这种不均衡的分布正在重塑产品团队。聚光灯正从实现工作转向理解工作。那些一直让最优秀的 PM 脱颖而出的核心技能——理解用户需求、清晰地定义问题、设计优雅的解决方案——价值呈指数级上升。

最优秀的 PM 把这些洞见转化为规格——让团队对齐、指引实现、并在一个日益自动化的开发世界里成为持久产物的规格。
