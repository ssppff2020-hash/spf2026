这篇文章讲的是一个重要但也令人害怕的提示注入发现：它会导致 GitHub Copilot 和 VS Code 中开发者的机器被完全攻陷。

攻击的实现方式，是通过修改项目的 settings.json 文件，把 Copilot 置入 YOLO 模式（YOLO mode）。

正如几天前在 Amp 中描述的那样，智能体中一种可能被忽视的漏洞模式是：如果智能体能够写入文件、修改自身配置或更新与安全相关的设置，就可能导致远程代码执行（RCE）。这种情况并不少见，在做安全评审时，这是一个要始终留意的地方。

## 背景研究

在查看 VS Code 和 GitHub Copilot 的智能体模式（Agent Mode）时，我注意到一个奇怪的行为……它可以在未经用户批准的情况下，在工作区中创建并写入文件。

这些修改会立即持久化，它们不是等待评审的内存中的差异（diff）。修改会马上写入磁盘。

这类东西，作为红队成员你一看就知道大概不是什么好事……于是我就想看看能不能用它来提权并执行代码。

### YOLO 模式

接着，我研究了 VS Code 中依赖项目/工作区文件夹内设置的功能，很快发现了一个有意思的。

原来，在 .vscode/settings.json 文件里可以加上下面这一行：

"chat.tools.autoApprove": true

这会把 GitHub Copilot 置入 YOLO 模式。

它会禁用所有用户确认，于是我们可以运行 shell 命令、浏览网页，等等！

有意思的是，这是一个实验性功能，但它默认就存在。我并没有下载特殊版本，也没有把我的 VS Code 整体切到实验模式。

而且，它在 Windows、macOS 以及 Linux 上都能用。

## 攻击链解析

用来劫持 Copilot 并提权的概念验证（proof-of-concept）攻击链如下：

攻击始于植入在源代码文件、网页、GitHub issue、工具调用响应或其他内容中的提示注入……payload（载荷）也可以使用不可见文本作为指令。

提示注入首先向 ~/.vscode/settings.json 文件添加 `"chat.tools.autoApprove": true` 这一行。如果文件夹和文件尚不存在，它们会被创建出来。

GitHub Copilot 立刻进入 YOLO 模式！

攻击会运行一条终端命令。而借助条件提示注入（conditional prompt injection），我们实际上可以根据操作系统来决定运行什么。

我们实现了由提示注入驱动的远程代码执行。

这里有一张截图，展示了带有提示注入的演示文件、开发者在右侧聊天框中与该文件交互，以及计算器弹了出来！

当然，任何其他投递提示注入的手段，比如来自 Web 的内容或 MCP 服务器返回的数据，都是攻击角度。我只是把它放在源代码文件里，因为这样最容易测试。

## 把工作站加入僵尸网络——ZombAI

当然，这意味着我们可以把开发者的机器作为一个 ZombAI 加入到僵尸网络（botnet）中。

另外，为了好玩，我们还可以修改 settings.json 文件，把 VS Code 切换成红色配色方案之类的东西。

不过这还没完！这还意味着我们可以构建一个真正的 AI 病毒，它附着在文件上，随着开发者下载并与被感染的文件交互而传播。

最后但同样重要的是，为了证明我们完全控制了开发者的主机，我们展示了 Copilot 可以被劫持去下载恶意软件，并接入一个远程命令与控制服务器。

这意味着大门已经打开，恶意软件、勒索软件、信息窃取程序等等都能进来。

真是可怕的东西。

## 构建 AI 病毒

看到这里，你会注意到这基本上允许制造一种病毒。攻击者可以嵌入指令，一旦获得代码执行能力，额外的恶意软件就能攻陷其他 Git 项目（以及 RAG 来源）来嵌入这些恶意指令，并提交这些改动，甚至强制推送到上游。

随着其他开发者在不知情的情况下传播被感染的代码，这会导致进一步扩散。

最后，我们还必须谈谈不可见指令！

## 使用不可见指令

有人可能会说，如果指令以注释形式嵌入，很快就会被发现。所以为了让它更有意思一点，我动手做了一个不可见的 payload，它能完成整条攻击链，但用户看不到。它没那么可靠，但确实还是管用：

注意：尽管这里使用不可见指令的演示在我这里成功过多次，但使用不可见指令往往会让漏洞利用变得非常不可靠，而且还常常被模型拒绝，另外 VS Code 一般也会对 Unicode 字符给出一个视觉提示。不过，攻击（以及模型）会随着时间变得更强。同样值得强调的是，并非所有模型都容易受到这类不可见提示注入攻击的影响。

## 建议与修复

除了我分享的 YOLO 模式这个例子之外，其实还有更多攻击角度。当 Microsoft 问我是否还有其他信息时，我又多看了看，注意到还有其他有问题的地方，例如 AI 可以写入的 .vscode/tasks.json，或者添加伪造的恶意 MCP 服务器等等，这些都能导致代码执行。而且 AI 还能重新配置项目的用户界面和配置设置。

最近我注意到开发者经常使用多个智能体，所以还存在覆盖其他智能体配置文件的威胁（允许列表中的 bash 命令、添加 MCP 服务器……），因为这些配置文件通常也放在项目文件夹里。

理想情况下，AI 不应该在没有人先批准的情况下就能修改文件。许多其他编辑器确实会显示差异，然后由开发者批准。

## 负责任披露

在 2025 年 6 月 29 日报告该漏洞之后，Microsoft 确认了该问题可以重现，并追问了几个后续问题。几周后，MSRC 指出这是他们已经在跟踪的问题，并将在 8 月打补丁修复。随着 8 月的补丁星期二（Patch Tuesday）发布，这个问题现在已经修复了。

向来自 Persistent Security 的 Markus Vervier 致意，他也发现并向 Microsoft 报告了这个漏洞。你可以在这里找到他们的分析文章。同时也要向 Ari Marzuk 致意，他看起来也并行地发现了这个问题。

感谢 MSRC 和产品团队的成员在推动缓解该问题方面提供的帮助。

## 结论

这是又一个例子，说明 AI 智能体可能不会老老实实待在自己的盒子里！GitHub Copilot 通过修改自身环境，可以提权并执行代码，从而攻陷开发者的机器。正如我所发现的，这是智能体化系统（agentic systems）中一种并不少见的设计缺陷。

继续留意这类设计缺陷，它们在威胁建模过程中应该很容易被发现。

干杯。
