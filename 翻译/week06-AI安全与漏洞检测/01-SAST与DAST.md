## 什么是 SAST？

静态应用安全测试（SAST）是一种白盒安全测试方法。SAST 使用应用的静态源代码或二进制文件来识别漏洞。这意味着 SAST 工具在应用未运行时对应用代码进行操作。

开发者用 SAST 检测各种安全风险，例如：跨站脚本（XSS）、不安全的反序列化、缓冲区溢出，以及代码中的其他 OWASP 漏洞。由于单靠 SAST 无法识别运行时特有的漏洞，开发者往往必须把 SAST 与其他测试方法结合使用，才能实现全面的安全。

SAST 是软件开发生命周期的重要组成部分，因为它能及早发现漏洞。发现得越早，修复成本就越低。由于 SAST 工具可以在开发阶段运行，开发者现在能在产品发布上市之前，把代码写出来并测试上千次（！！）。

SAST 可以集成到持续集成/持续交付（CI/CD）流水线中，这样做时被称为「安全 DevOps」或「DevSecOps」。SAST 通过自动化具有很好的可扩展性。能够实现覆盖 SAST 技术的自动化测试，使 SAST 成为一种快速应对代码级风险的高效方案。

## 什么是 DAST？

动态应用安全测试（DAST）是一种黑盒测试方法。DAST 中的「Dynamic」（动态）一词表明，这种方法在应用运行时评估其安全性。与 SAST 不同，DAST 不需要访问应用的源代码。相反，它：

- 模拟外部攻击者的行为。
- 从外部测试应用，识别只在运行时才会出现的漏洞。

DAST 能够识别各种安全缺陷，例如拒绝服务（DoS）漏洞和不安全的服务器配置。通过模拟真实世界的攻击场景，DAST 工具评估应用如何响应这些模拟威胁。借助这种方法，开发者能找出 SAST 等静态测试方法可能漏掉的弱点。

通常，开发者在软件开发生命周期的后期执行 DAST，往往就在部署之前。通过在真实运行环境中测试应用，DAST 能清晰呈现运行时安全的整体状况，并帮助打造性能更好、能抵御潜在攻击的应用。

## SAST 是如何工作的？

开发者使用 SAST 工具应用预定义规则和其他检测方法——例如模式匹配和数据流分析——来识别编码错误和其他漏洞。他们把这些工具集成到 IDE 或 CI/CD 流水线中，在编码和测试阶段自动执行扫描。

### 常见的 SAST 方法

以下是 SAST 中使用的一些方法。

模式匹配会扫描代码库，查找已知的不安全编码实践模式。例如使用弱加密算法或不安全的 API 调用。

数据流分析追踪数据在应用中的流动。它通过追踪不可信输入到敏感操作的路径，可以识别 SQL 注入或缓冲区溢出这类漏洞。

> 译注：原文此处为「Data flow C」，疑为抓取时链接文本残缺，按上下文应为「Data flow analysis」（数据流分析）。

控制流分析可以分析应用的控制结构，例如循环和条件分支，从而发现逻辑缺陷或竞态条件这类潜在漏洞。

自定义规则创建。许多工具允许开发者创建自定义规则，以落实编码最佳实践。以下是这些自定义规则的一些例子：

- 标记 SQL 查询中任何未净化输入的用法。
- 识别把用户提供的数据未经适当转义就输出到浏览器的代码。
- 高亮使用有漏洞或已废弃函数的地方，例如 JavaScript 中的 eval() 或 C 中的 strcpy()。
- 检测源代码中出现的硬编码 API 密钥和密码，并标记任何对用户提供的数据缺少输入校验的情况。

依赖扫描。一些 SAST 工具会分析应用中使用的第三方库和框架，以识别依赖中的漏洞。

语义分析。通过理解代码的含义而不仅仅是结构，SAST 工具能检测不安全的配置或 API 的误用。

机器学习模型：先进的 SAST 工具引入机器学习算法，通过分析大规模数据集中的模式来识别以前未知的漏洞。

### 使用 SAST 工具时的性能考量

SAST 工具通常需要大量 CPU 和内存资源。在分析大型代码库时，这可能是个大问题。对一百万行代码做一次完整扫描，可能会消耗数 GB 的 RAM。

SAST 扫描所需的时间会随代码库大小剧烈变化，小项目可能只要几分钟，企业级应用则可能要几个小时。这可能影响：

- 构建流水线的时间进度
- 开发者的工作效率

可以考虑使用支持增量扫描的现代 SAST 工具，这样你就只需分析改动过的代码，而不必分析整个代码库。

此外，通过规则选择和范围界定来做性能调优至关重要。配置不当的 SAST 工具会不必要地分析非关键代码路径，白白浪费时间和资源，却带不来任何安全收益。

## DAST 是如何工作的？

DAST 工具模拟真实世界的攻击——例如向输入字段发送各种形式的恶意数据，看应用如何处理——以识别应用行为和响应中的漏洞与弱点。

### DAST 的步骤

这个过程通常包含以下步骤。

第 1 步：扫描。扫描 Web 应用，发现入口点（例如 URL、表单和 API）。这一步梳理出应用的结构，并识别潜在的攻击面。

第 2 步：攻击模拟。通过向应用发送精心构造的请求来模拟恶意活动。这些请求尝试利用入口点，以测试跨站脚本和跨站请求伪造这类漏洞。

第 3 步：漏洞检测。分析应用的响应以识别安全弱点。它评估应用在受攻击时行为是否符合预期。例如，可以注入恶意数据来检测 SQL 注入缺陷。

第 4 步：报告。生成包含所检测到的漏洞和修复建议的报告。开发者可以利用报告中的结果来修复已识别的问题。

现代 DAST 方案可以包含 AI 驱动分析和实时数据集成等高级功能。它们自动创建测试集，动态适应应用的结构，并利用机器学习算法把误报降到最低。

### 使用 DAST 工具时的性能考量

以下是使用 DAST 工具时需要留意的几个性能瓶颈。

- DAST 工具会主动与正在运行的应用交互，短期内会推高应用服务器和 Web 服务器的 CPU 与内存占用。
- DAST 扫描期间产生的大量并发请求会消耗可观的网络带宽。
- DAST 扫描器经常通过生成唯一请求来绕过或使应用缓存失效，降低了缓存机制的效果。
- DAST 工具创建和管理多个测试会话，会增加应用服务器的内存占用。

要避免这些问题，或尽可能减小它们的影响，请遵循以下做法。

- 把 DAST 扫描安排在应用使用量最小的非高峰时段。
- 在镜像生产环境配置的预发布或预生产环境中执行扫描。
- 使用 DAST 工具中的限流功能来控制同时请求的数量。
- 在扫描期间扩大应用服务器的线程池。
- 为 DAST 扫描器的 IP 配置单独的缓存策略。
- 如果超过性能阈值，实现自动暂停扫描。

## SAST 与 DAST：关键区别

下表总结了 SAST 与 DAST 的区别。

| 对比维度 | SAST | DAST |
|---|---|---|
| 测试类型 | 白盒测试。可以访问源代码，从内向外测试应用。 | 黑盒测试。不能访问源代码，从外部测试应用。 |
| 支持的软件类型 | 支持多种软件类型，包括 Web 应用、Web 服务和胖客户端。 | 支持 Web 应用和 Web 服务，但通常不支持其他软件类型。 |
| 在 SDLC 中的阶段 | 在软件开发生命周期的早期执行。 | 在 SDLC 的后期执行，通常在部署期间或部署之后。 |
| 检测到的漏洞 | 识别编码缺陷，例如：SQL 注入、跨站脚本（XSS）、缓冲区溢出等。 | 检测运行时问题，例如服务器配置错误、拒绝服务漏洞和应用层缺陷。 |
| 修复漏洞的成本 | 较低，因为问题在 SDLC 早期就被发现。 | 较高，因为漏洞发现得晚，通常需要紧急修复才能按时部署。 |
| 运行时与环境问题 | 无法检测运行时特有的或与环境相关的漏洞。 | 能识别只在运行时出现或因环境因素而出现的漏洞。 |
| 深度与广度 | 对代码级漏洞提供深入洞察。 | 提供应用外部安全风险的广角视图。 |
| 与工具的集成 | 与 IDE 和 CI/CD 流水线集成，实现自动化静态分析。 | 与 CI/CD 流水线集成，实现持续的运行时测试。 |
| 误报与漏报 | 由于深入分析代码，误报概率更高。 | 误报更少，但由于内部可见性有限，漏报风险更高。 |
| 技术依赖 | 依赖编程语言和框架；需要工具与之兼容。 | 不依赖应用框架，因为它们从外部与应用交互。 |

## SAST 与 DAST 的优缺点

### SAST 的优点

- 在软件开发生命周期早期识别安全漏洞。
- 分析代码库，包括基本函数和复杂分支。
- 直接对源代码进行操作，不需要应用运行。
- 提供实时反馈和全面的洞察，例如漏洞的确切位置。
- 生成可导出的报告，可以用仪表盘跟踪。
- 支持自动化，因此比人工代码评审更快、更高效。

### SAST 的缺点

- 常常产生大量误报，因此可能需要人工复查。
- 无法识别运行时特有的或环境相关的漏洞，例如配置错误。
- 每种编程语言都需要专门的工具，因此维护复杂。
- 在理解外部库、API 和 REST 端点方面比较吃力。

### DAST 的优点

- 识别只在应用执行期间才出现的漏洞。
- 从外部操作，不需要访问源代码。这对测试第三方应用或已编译的代码很有效。
- 模拟真实的攻击场景，识别被 SAST 漏掉的风险。
- 独立于应用的编程语言工作。
- 评估整个应用和系统，包括内存消耗、资源使用和第三方接口。

### DAST 的缺点

- 只关注应用的外层，可能漏掉更深层的漏洞。
- 在 SDLC 后期才应用，因此修复更昂贵、更耗时。
- 会漏掉某些 SAST 工具通过源代码分析能识别的漏洞。举个例子：一个 Web 应用使用不安全的随机数生成器（例如 JavaScript 中的 Math.random()）来生成会话令牌。DAST 可能漏掉这个缺陷，因为它只测试运行时行为。（但 SAST 能检测到它。）
- 大型项目需要定制基础设施，需要运行多个应用实例并行工作，因此资源消耗大。

## 我该在什么时候用 SAST、什么时候用 DAST？

SAST 和 DAST 在保障 SDLC 安全方面扮演互补的角色。理解各自适用的时机，有助于实现全面的安全覆盖。

### 什么时候用 SAST

在开发早期阶段。开发者在 SDLC 早期用 SAST 识别 SQL 注入和硬编码凭据这类漏洞。在部署前就发现这些问题，可以降低修复的成本和复杂度。

例如：SAST 工具扫描 Python 代码，标记出一处硬编码 API 密钥嵌在源代码中的漏洞。开发者重构代码，改用环境变量来安全地存储和读取密钥。

用于代码评审。SAST 可以集成到版本控制系统中，让开发者在提交代码之前先扫描。这样能确保只有安全的代码进入代码仓库。

示例：SAST 工具能检测出直接用未经校验的用户输入拼接文件路径的漏洞，它会让应用暴露在路径遍历攻击之下。开发者通过净化输入并使用安全的库函数处理文件路径来修复该问题。

在持续集成/持续部署流水线中。SAST 在 CI/CD 过程中运行自动化扫描，为开发者提供实时反馈。

### 什么时候用 DAST

预生产测试。开发者在预发布或质量保障（QA）环境中用 DAST 识别运行时漏洞（例如：不安全的配置、身份验证缺陷、访问控制不足）。

示例：DAST 工具能检测出导致敏感数据暴露的数据库配置错误。随后开发者可以在部署前加固该配置。

在部署后监控中。DAST 工具持续扫描已部署的应用，查找由环境变化或新出现的威胁导致的漏洞。这保证了应用长期保持安全。

测试第三方集成。DAST 可以模拟外部攻击者的视角，识别第三方 API 或互连系统中的漏洞。

例如：DAST 工具测试一个 Web 应用时，发现第三方支付 API 中存在一个漏洞：信用卡信息通过未加密的 HTTP 连接传输。开发者通过强制所有 API 通信使用 HTTPS 来解决该问题。

## 哪个更有效：SAST 还是 DAST？

SAST 或 DAST 的有效性取决于：

- SDLC 所处的阶段
- 所针对的漏洞类型

SAST 在开发早期效果最好，主要用于识别源代码中的漏洞、降低成本、推行安全编码实践。相比之下，DAST 专注于预生产或已部署应用的运行时漏洞，它能揭示配置错误和不安全的集成这类问题。

### 采用混合方案

与其二选一，不如把 SAST 和 DAST 结合起来，形成多层安全策略，同时覆盖静态代码和运行时环境中的漏洞。SAST 可以集成到开发早期阶段，在应用编译之前就检测并修复代码级问题。一旦应用在测试环境中运行起来，DAST 就能识别运行时漏洞，并评估应用在受攻击条件下的行为。

在 CI/CD 流水线中同时自动化 SAST 和 DAST 扫描，可以提供持续反馈，在不牺牲安全的前提下加快开发进程。

对于敏捷或 DevOps 环境，加入 IAST 或 RASP 这类工具可以进一步增强安全性。通过关联 SAST 和 DAST 的结果，组织可以实现更全面、更有效的漏洞管理。

### 用 RASP 作为 SAST 和 DAST 的替代方案

运行时应用自我保护（RASP）是一种安装在应用所运行服务器上的高级安全方案。

RASP 把自己嵌入应用的运行时环境。这种集成让 RASP 能够分析应用的逻辑和数据。在分析过程中，它可以：

- 在异常行为发生时将其检测出来。
- 立即阻断恶意活动。

一个关键区别是，RASP 不只是对潜在问题发出告警——它主动隔离并解决威胁来阻止攻击，不依赖外部工具。

RASP 为 SAST 和 DAST 提供了一种动态的替代方案。与分析静态代码的 SAST 和模拟外部攻击的 DAST 不同，RASP 实时运行。它监控应用在执行期间的行为，并通过终止会话或提醒防御人员来应对实时威胁。

RASP 在保护应用免受绕过网络防御或在开发期间被漏掉的漏洞方面尤其有效。

然而，过度依赖 RASP 可能让组织忽视安全编码实践。此外，RASP 可能会影响应用性能，因为它直接在应用的运行时环境中运行。RASP 不能取代修复底层缺陷的必要性，但它能在修复进行期间提供持续保护。

正如一位 RASP 用户的评论：

「决定是否使用 RASP 工具，应该基于对应用具体需求和风险状况的全面评估。」

## 未来是 SAST、DAST 与 RASP 结合的应用安全测试

应用测试的未来在于把 SAST、DAST 和 RASP 结合起来，形成全面的安全策略。随着安全挑战加剧，把这些工具集成到 CI/CD 流水线并自动化其流程将变得不可或缺。

AI 和机器学习的进步将提高测试效率，因为它有助于减少误报并改进威胁检测。

### 金融与金融服务业

在金融行业，AI 驱动的工具将改变漏洞的检测和缓解方式。SAST 和 DAST 将继续在开发和预生产阶段识别编码缺陷和运行时问题。

但不会止步于此：RASP 会利用 AI 监控实时交易，把它推进得更远。例如，RASP 可以检测出异常模式（例如：攻击者试图实时利用某个漏洞），阻断这些活动并通知安全团队。

### IoT、边缘计算与联网设备

在 IoT 方面，这些工具的组合将在保障联网设备安全上发挥重要作用。具体如下：

- SAST 可以在开发期间确认固件没有漏洞。
- DAST 可以测试设备之间通信协议的安全性。
- 而 RASP 监控已部署的设备，检测并阻止未授权访问尝试，或新出现的威胁导致的数据泄露。

同样，使用多种方法有助于 IoT 生态系统保持韧性。正如我们在众多示例中说明的那样，SAST、DAST 和 RASP 结合在一起，将带来一个以更强、更主动的安全措施来构建和部署应用的未来。

## 有韧性的安全始于主动测试

把 SAST、DAST 和 RASP 结合起来，可以提供覆盖整个软件开发生命周期的强健安全性。

把这些方法集成到 CI/CD 流水线并利用 AI 的进步，组织可以主动应对新出现的威胁。这些方法共同提供了一套整体方案，保护现代应用免受安全漏洞的影响。
