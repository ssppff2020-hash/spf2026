TL;DR：我们评测了 AI 编程智能体在真实代码中寻找漏洞的效果如何。

做法：我们让 Anthropic 的 Claude Code（v1.0.32，Sonnet 4）和 OpenAI Codex（v0.2.0，o4-mini）去 11 个流行的大型开源 Python Web 应用中寻找漏洞。两者合计产生了 400 多条安全发现，由我们的安全研究团队逐条审阅。

AI 编程智能体能找到真实漏洞：Claude Code 找到 46 个漏洞（真阳率 TPR 14%，误报率 FPR 86%），Codex 报告 21 个漏洞（TPR 18%，FPR 82%）。其中约 20 个是高危漏洞。

AI 能抓住上下文，却在数据流上卡壳：Claude Code 最擅长发现不安全的直接对象引用（IDOR）缺陷，真阳率（TPR）为 22%（59 条报告中 13 条正确），但在跨多个文件和函数做污点追踪时很吃力：SQL 注入的 TPR 只有 5%（2/38），XSS 为 16%（12/74）。

OpenAI Codex 没能报告任何正确的 IDOR，TPR 为 0%（0/5）；在 SQL 注入上表现极差，0%（0/5），XSS 也是 0%（0/28）；但出人意料的是，它报告的路径遍历（Path Traversal）正确问题比 Claude Code 更多，TPR 为 47%（8/17）。

非确定性是真正的难题：在完全相同的代码库上多次运行完全相同的提示词，结果往往大相径庭。在某个应用中，三次完全相同的运行分别产生了 3、6 和 11 条不同的发现。

关键结论：

- 只要给出相对简单的、聚焦安全的提示词，AI 编程智能体就已经能在真实应用中找到真实漏洞。
- 但是：取决于漏洞类别，结果可能相当嘈杂（误报率高），尤其是在 SQL 注入、XSS 和 SSRF 这类传统的注入式漏洞类别上。
- 详细的评测和基准测试是理解某种方法在找漏洞上有多有效的关键（这一点一直成立，但在 LLM 这类非确定性工具出现后更是如此），也是判断你的改进是否朝着正确方向前进的关键。

## 引言

在 Semgrep，应用安全（AppSec）就是我们的命根子。我们很早就在产品中把 AI 投入生产使用（Assistant 背后的技术、用 promptfoo 测试我们的 AI 工作流、用安全研究员的研判来评测自动研判的表现），一直在研究传统确定性分析与现代 AI 上下文能力的最佳组合，而不去追逐潮流。

这项研究是这一长期使命的一部分。我们正在开展一次深入、公开的探索，回答一个人人都在想的问题：LLM 在源代码中找漏洞到底有多有效？

## 关于基于 AI 的漏洞挖掘的开放研究问题

为了引导研究，我们把「LLM 擅长找 bug 吗？」这个宽泛问题拆解成更具体、可度量的子问题。

基于 LLM 找漏洞的误报率和漏报率是多少？它会随编程语言、框架、代码库规模或漏洞类别而变化吗？它对代码的写法有多敏感？

造成误报和漏报的常见原因有哪些？

这种分析有多确定？每次都能得到相同结果吗？

具体到注入类漏洞，我们想知道：

- LLM 在源点（例如用户提供的值）与汇聚点（例如消费原始 SQL 查询的方法）之间追踪用户输入的效果如何？
- 它能跨函数、跨文件追踪数据吗？
- 它能对净化函数和其他安全控制做出推理吗？
- 它能对来自第三方开源依赖的函数做出推理吗？

## 常见 SAST 基准测试的问题：缺乏真实性

在深入讲我们的发现之前，先聊聊我们如何衡量 AI 的表现。当前的很多研究／主张都依赖某些基准测试；这些基准测试虽然有价值，却没有完全体现真实世界代码的复杂度。

带已知漏洞的应用：这些基准只使用存在已知漏洞的开源应用；多亏 Kinnaird McQuade，其中很多都能在 vulnerable-apps 里找到。如果你读过这个博客，可能认得 WebGoat、JuiceShop、OWASP Benchmark 等名字。但这些基准有个问题：当前的 LLM 很可能已经摄入过这些仓库的代码，以及互联网上大量的公开文章，这让它们拥有先验知识，从而使结果产生偏差。

它们的代码往往不真实，充斥着大量注释、标注和变量名，暗示甚至直接说明漏洞在代码的什么位置、或者如何利用。有时工具的运行结果甚至被直接签入仓库。

XBOW 为自动渗透测试工具提供了基准，但不适合静态分析：代码往往过于人为和简化，不能代表真实应用。ZeroPath 做了很好的清理工作，但只有一小部分被清理过。此外，这些测试用例每一个都是很小的应用，为模拟某个专门的攻击场景而设计。如果只看 Python 基准，XBOW 有 45 个；45 个各不相同的小应用，平均不到 98 行代码、3 个 Python 文件。这太小了，无法涵盖在整份代码库或众多函数中搜索与推理的复杂度。

CVE 记忆偏差：LLM 是在来自互联网的海量公开数据上训练的，其中就包括发现并修复 CVE 的那些代码库本身。这就造成根本性的数据污染问题。AI 可能并不是通过新颖的分析发现了漏洞，而只是认出了它在训练时记住的模式。

最近学术界设计了 CyberGym、Eyeballvul、SecVulEval 等基准。它们有显著改进，更接近真实世界的例子，但没有聚焦现代 Web 应用，或者把漏洞从更广的应用上下文中孤立出来。

EyeballVul：Timothée Chauvin 提出的较新基准，从开源项目中提取经人工审核的真实世界漏洞，并以最小化的、可复跑的测试用例呈现。虽然基于真实代码，它仍然把漏洞从更广的应用上下文中孤立出来，使搜索问题变得更简单。

SecVulEval 和 CyberGym：这些套件用于评测 C 或 C++ 中的漏洞。它们在自己的领域内很有价值，但对 C 和 C++ 的专注意味着这些数据不适用于主导现代云原生开发的 Python/JavaScript 以及其他以 Web 为中心的语言。

这些方法各有用途，有时也确实该用，但它们未必反映现代软件开发的实际状况。真实世界的应用不是干净、孤立的函数，而是依赖、框架和业务逻辑交织成的复杂网络。

我们的方法不同。我们测试了 11 个大型、基于 Python、持续维护的开源项目，它们使用常见的 Web 框架（Django、Flask、FastAPI）编写。我们的方法与前面那些互补，我们认为它的独特之处在于：a) 力求代表真实世界中 AI 驱动的漏洞发现（而不是小型、孤立的合成示例）；b) 没有被模型训练数据污染；c) 代表了大多数开发者和公司实际在构建的应用类型——使用现代语言和框架的 Web 应用。

我们在 11 个应用上运行了分析，然后人工研判了全部 445 条发现，其中大多数（尤其是 IDOR 和认证绕过）做了动态验证。

### 我们的发现

Claude Code 和 Codex 今天都已可用：它们能找到真实的安全漏洞，但非常嘈杂。整体噪声仍然很高，但它们确实在这些热门的开源 Python Web 应用中找到了真实的安全漏洞。总体而言，Claude Code 找到 46 个漏洞（TPR 14%、FPR 86%），Codex 报告 21 个漏洞（TPR 18%、FPR 82%）。

许多 IDOR 缺陷乍看是对的，Claude Code 还给出了可信的修复方案：LLM 不仅能找到这些缺陷，还能提出可信的修复，比如依据代码中已有的模式注入新的权限检查。IDOR 问题很难研判，我们必须测试其中大多数才能确定，这使得真阳率低得多。

Claude Code 是个好用的安全护栏工具吗？许多发现虽然在技术上属于误报，但仍然是、或看起来是合理的「护栏」建议。例如，模型常常建议把一条本来就安全的 SQL 查询参数化。这虽然不算漏洞，却能增强代码。我们仍把它们算作误报，只是没有其他误报那么严重。

不过，这些代码加固建议并不总是可信。我们发现了若干案例，尤其是在客户端 JavaScript 代码中，AI 试图修复它认为存在的 DOM 操作问题，结果反而破坏了代码（在我们观察到的案例中是 HTML 被双重转义），而那里本来根本不存在安全问题。

XSS 和 SQL 注入——难以把各个组件拼起来：模型很难追踪数据从服务端框架到客户端组件（XSS 的常见模式）的流动，或穿越复杂的应用分层。它常常被静态定义的数据搞混，或者识别不出服务端的净化处理。

重复提示词有助于得到更多结果：LLM 的概率本质意味着，稍微换个方式问同一个问题就可能得到新的发现，凸显了分析的不一致性。在同一份代码库上多次重复同一提示词会给出不同答案，但最终又会绕回同样的发现。

OpenAI Codex 有时无法报告有效的 SARIF。在我们预期的 66 份报告中，有 9 份不是有效的 SARIF。我们仍然考虑了那些文件里报告的全部发现，尽管它们不是有效的 SARIF 或 JSON。Claude Code 在我们尝试的任何案例中都没有这个问题。

## 同样的代码、同样的 AI，每次却报出不同的 bug：AI 编程智能体的非确定性难题

为了探究非确定性在实际中如何表现，我们从中挑选了三个应用，针对同一个安全问题——IDOR——用同一个提示词多次运行。一个模式浮现出来：我们每一次运行测试，AI 的发现都不一样。

在漏洞检测的语境下，这是个大问题。首先，作为安全工程师，我们理想上希望得到比「希望这次模型搜得够彻底」更强的保证，来确认代码中的关键漏洞类别已被扫描。

其次，间歇性地检出漏洞会在你的安全工具或漏洞管理系统中造成不一致和噪声。例如，如果你在用 SAST 平台、ASPM 或自建的系统，这些系统常常假定：当某个此前检测到的漏洞不再出现时，它就已被修复。但在 LLM 驱动的检测中未必如此，因为单次扫描可能漏掉它，于是后续扫描重新发现同一问题时就会创建一条「新」发现，导致重复的 JIRA 工单和开发者的挫败感。

以下是我们观察到的一些具体例子：

- PY-APP-007：第一次运行中，AI 识别出一个「缺少搜索授权」的漏洞，另外两次运行都没有它。第二次运行标记了该次运行独有的问题。第三次运行则发现了它自己特有的一组漏洞。
- PY-APP-006：情况类似：第一次运行挖出了用户 API 中的一个漏洞，而后续运行则聚焦于代码库的其他部分，例如 event abstracts 和 notes 模块。
- PY-APP-002：这里的波动也许是最大的。识别出的漏洞数量从第一次运行的 3 个跳到第二次的 6 个，再到 11 个。每次运行给出的发现都不同，只有部分重叠。

那么，这背后是什么？我们认为关键因素是所谓的上下文腐化与压缩（compaction）。当一个 AI 智能体被要求分析整个代码库时，它要处理海量信息：上下文腐化会导致它无法从自己的上下文中准确检索。为了应对这一点，LLM 使用一种有损压缩（有时称为 compaction），这意味着函数名、路径等更细的推理细节可能在摘要过程中丢失。

把它想象成给一部长篇复杂小说写摘要。你能抓住主要情节，但必然会漏掉一些微妙和细枝末节。同样，AI 可能会跟丢某个特定的架构模式或隐蔽的数据流，导致它在某一次运行中漏掉某个漏洞，而在另一次运行中却能抓到。我们在 PY-APP-006 中看到了一个清晰的例子：AI 提出的某个修复不完整，因为它没有复用已有的用户授权基类——而这一关键上下文似乎在那次运行中丢失了。

这种非确定性对我们如何开展 AI 原生 SAST 有重大影响。一方面，AI 每次「思考」方式都不同，意味着它能探索更广的潜在攻击向量，就像一支视角多元的人类渗透测试团队。另一方面，它也引入了不确定性，可能导致混乱或异常行为。

- 覆盖不完整：单次运行可能带来虚假的安全感，因为它可能漏掉后续运行才能抓到的关键漏洞。
- 缺乏可重复性：无法复跑结果，使得验证 AI 的发现、并以一致、可重复的方式信任其输出变得困难。
- 成本与时间增加：为了得到更完整的图景而需要运行多次审计，会显著增加所需的时间和计算资源。注意：对于传统软件，一旦写好，你基本上可以「免费」再运行一次（硬件成本、电费等除外）。重度依赖 LLM 的工具则不然：在这里，读入一份代码库并对其推理，每次扫描可能产生几十到几百美元的 token 成本。对今天的模型而言，这个成本可能会随时间下降，但更新的模型可能更贵。

## Claude Code 新的 /security-review 命令有多有效？

Anthropic 为 Claude Code 发布了一个新命令，叫 /security-review。它被设计为在拉取请求上运行，检查改动过的文件并提问，以识别具体的安全问题。你可以在这里找到该提示词。

把这条命令跑在整个代码库上时，我们发现它识别出的安全问题相当有限。很多时候，我们一次只让 Claude Code 搜索某一类具体安全问题所能得到的那些问题，它都找不到。

我们在 PY-APP-003、PY-APP-002 和 PY-APP-008 上运行了这条命令，三者加起来只找到一个 XSS，这与我们在整体实验中得到的结果相差很大。

## 回答我们的问题

让我们根据学到的东西，回顾最初的研究问题。

误报／漏报率是多少？对于在真实世界代码上直接使用 AI，误报率非常高：最好情况是 Codex 的路径遍历 53%，或 Claude Code 的 IDOR 78%；最差情况是 Claude Code 的 SQL 注入 95%，以及 Codex 的 SQL 注入或 IDOR 100%。表现还随应用剧烈变化：从 PY-APP-002（Claude Code）的 100%（10/10）真实 IDOR，到 PY-APP-007 的 0%（0/7）。跨所有应用和所有报告的问题，Claude Code 找到 46 个漏洞（TPR 14%、FPR 86%），Codex 报告 21 个漏洞（TPR 18%、FPR 82%）。

由于我们用的是真实应用，本实验无法准确测量漏报率。我们会在后续博客中介绍测量漏报率的技术！

它为什么会失败？我们观察到的主要弱点是：在注入类问题上，模型缺乏对代码执行的深层语义理解。模型在过程间污点流（inter-procedural taint flow）和隐式流上很吃力，而这正是传统 SAST 引擎通常擅长的。部分局限也来自上下文压缩和上下文腐化。我们会继续更细致地探索这些局限，并寻找缓解它们的方案。

scaffolding 和智能体化工作流有多重要？它们不只是重要，而是正变得不可或缺。AI 在安全评审中的未来不是一个单一、庞大的模型，而是一个 AI 智能体系统（包括我们案例中的这类编程智能体），它们能使用工具、对证据进行推理，并协作发现和验证漏洞。

虽然我们（目前）还没有数据来比较「使用能访问 Claude Code 的智能体」与「用更典型的上下文工程（即构建 scaffolding 来提供所有相关代码）配推理模型」，但我们观察到，系统在处理复杂流程、并在报告安全问题的过程中做出有根据的决策的能力上差异巨大。话虽如此，一个反例是 Sean Heelan 通过做足够多的上下文工程，让推理模型报告出了一个漏洞（成功率为 8%）。我们强烈建议你读一读他的博客文章。

这一切的成本如何？遗憾的是，我们没能一致地追踪 Claude Code 和 Codex 之间的成本。Claude Code 的总成本是 114 美元，覆盖所有这些漏洞和所有这些应用（非确定性运行和 /security-review 命令除外）。

## 数据集：未来发布

我们今天不会发布数据集，也不会公布所分析开源应用的名称，因为我们正处于负责任披露的过程中，正在联系应用开发者，让他们把所有安全问题修复并验证。等这些完成后，我们会放心地发布数据。

## 结论

LLM 不是明天就能取代人类安全工程师的银弹；事实上，在端到端发现高危注入式漏洞方面，它们相当弱。然而，它们是一个极其强大的工具。我们的研究表明，通过理解它们的优势（上下文推理）和弱点（代码的深层语义），并利用先进的静态分析引擎在它们周围构建精巧的智能体系统，我们能创造出远胜以往任何工具的新一代安全工具。
